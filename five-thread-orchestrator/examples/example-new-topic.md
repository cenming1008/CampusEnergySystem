# 场景

这是一个“新主题进入”的示例。

目标是演示：当用户提出一个新任务时，总控线程如何先判断它是否仍属于当前主主题，再决定是否需要新开主题、是否需要正式 PLAN，以及下一棒应该交给谁。

## 背景

当前主区正在推进“设备分类与对象分层建模优化”。

这时用户提出一个新任务：希望把仓库里仍残留的旧产品命名做分层治理，避免前后端线程顺手把整个仓库做成全量 rename。

这个任务和“设备分类与对象分层建模优化”不是同一个主题，因此总控线程不能直接把任务丢给前端或后端，而要先判断是否需要新开主题。

## 用户输入

用户说：

“请帮我看一下仓库里旧的 `MineEnergySystem`、‘煤矿综合能源管理系统’ 这类命名残留要怎么处理，先不要全仓替换，我想先分层判断哪些该改、哪些不该改。”

## 总控线程判断结果

- 当前主主题：设备分类与对象分层建模优化
- 是否属于当前主主题：不属于
- 是否建议新开主题：建议，新主题可命名为“命名迁移分层治理”
- 是否建议升级为正式 PLAN：建议，需要正式 PLAN 约束范围，避免误做全仓 rename
- 建议线程路径：规范 / 探索 -> 规范 -> 前端 / 后端 -> 验收
- 是否需要用户拍板：需要
  - 是否确认新开主题
  - 是否接受本轮只做分层与低风险收敛，不做运行时契约迁移

## 下一棒线程

- 下一线程：探索
- 为什么交给它：
  - 当前首先缺的是事实判断，不是实现
  - 需要先把残留命中分层，区分主入口文案、低风险说明文案、历史背景、运行时冻结层
  - 只有探索先把范围拆清，规范和实现线程才不会误扩范围

## 示例 prompt 输出摘要

下一棒 prompt 摘要可写成：

- 先阅读 `AGENTS.md`、主区、当前 PLAN 和产品定位文档
- 判断这批旧命名残留是否属于新主题
- 把命中分成“当前必须改 / 可以延后改 / 历史背景 / 暂时不要动”
- 输出最小修复路径，并回写 `current-status.md`、`handoff.md`

## 说明

这个示例主要说明：当用户提出的新任务与当前主主题不一致时，总控线程的第一职责不是选实现线程，而是先判断是否需要新开主题与正式 PLAN。
