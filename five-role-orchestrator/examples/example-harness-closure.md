# 示例：规则 -> 前端 -> 验收 闭环

本示例用于演示 `five-role-orchestrator` 升级为轻量 harness 后，如何从“分流”走到“可验证、可回写、可收口”的最小闭环。

## 场景

- 当前任务：设备台账页存在补偿类设备入口文案不一致，需要在当前主题内做前端收敛，并在完成后进入验收判断。
- 当前主主题：`设备监控页实时数据语义收敛专题`
- 推荐路径：`规则 -> 前端 -> 验收`

## 总控层输出要点

### 1. 路径判断

- 当前任务属于当前主主题内的前端收敛问题。
- 由于涉及“当前主题边界是否允许继续补文案/入口收敛”，先交规则角色锁边界。
- 规则锁定后，不需要后端介入，直接交前端。
- 前端完成最小改动和验证后，交验收角色判断是否阶段完成。

### 2. 下一棒角色执行协议示例

```md
# 角色执行协议

## 基本信息
- 当前主主题：设备监控页实时数据语义收敛专题
- 当前角色：规则
- 上一棒角色：总控
- 本轮目标：确认补偿类设备入口文案收敛是否仍属于当前主题，并锁定本轮前端允许范围

## 权限边界
- 本轮允许动作：锁主题边界、锁允许范围、锁非目标、锁验收口径
- 本轮禁止动作：不直接展开前端实现，不新增后端接口，不重写主区主题
- 本轮允许触达文件/目录：PLAN、current-status.md、handoff.md
- 本轮禁止扩张项：不把当前局部入口收敛升级为新主题或整体导航重构

## 验证协议
- 本轮最低验证：确认当前任务仍属于当前主题，且无需后端接棒
- 必须记录的验证结果：规则结论、允许范围、非目标、下一角色
- 验证失败时处理：若发现任务已超出当前主题，交回总控/预判

## 回写协议
- 必须回写文档：PLAN、current-status.md、handoff.md
- current-status.md 最少回写项：当前待办、当前角色路径
- handoff.md 最少回写项：下一角色、允许动作、禁止扩张项
- PLAN-*.md 更新条件：若当前轮次范围或验收口径发生变化

## 停机 / 升级规则
- 必须停止并上交的条件：发现需要新增接口、需要 breaking change、或已脱离当前主题
- 升级到规则的条件：本轮已在规则角色，无需再升级
- 升级到验收的条件：前端完成后且验证充分
- 需要用户拍板的事项：若要扩大到第二个页面或第二个主动作

## 完成定义
- 本轮完成条件：边界已锁定，前端可直接接棒
- 完成后默认下一棒：前端
- 若未完成应如何交接：交回总控/预判重新判断路径
```

### 3. 下一棒 prompt 示例

```md
# 当前主题
- 当前主主题：设备监控页实时数据语义收敛专题

# 当前路径判断
- 当前角色路径：规则 -> 前端 -> 验收
- 当前任务归属：当前主题内的前端入口文案收敛

# 下一棒角色
- 下一角色：前端
- 交接原因：规则已确认本轮仍属于当前主题，且无需后端介入

# 当前允许范围
- 本轮允许动作：只改设备台账页补偿类设备入口文案与相关前端展示
- 本轮允许触达：frontend 相关页面/组件、current-status.md、handoff.md

# 当前非目标
- 本轮不做：不改后端接口、不改设备类型建模、不做导航重构

# 当前风险
- 风险列表：若前端改动暴露接口语义不一致，应停止并交回预判/规则

# 权限边界
- 本轮禁止动作：不得顺手修改后端逻辑，不得扩大到其他设备类型页面
- 本轮禁止扩张：不得把当前入口收敛扩成整页重构

# 验证协议
- 本轮最低验证：前端构建或最小单测通过，页面入口文案收敛生效
- 必须记录的验证结果：改动页面、验证命令、是否仍需后端
- 验证失败时处理：失败则打回前端补齐；若暴露契约问题则交回预判/规则

# 回写协议
- 必须回写文档：current-status.md、handoff.md
- current-status.md 最少回写项：当前阶段、当前验证结论、当前剩余风险
- handoff.md 最少回写项：交给验收的原因、验收需关注项
- PLAN-*.md 更新条件：若前端改动改变范围或验收口径

# 停机 / 升级规则
- 必须停止并上交的条件：发现接口契约不稳定、任务越界、需新增后端能力
- 升级到预判的条件：根因不再清楚
- 升级到规则的条件：主题边界或非目标发生变化
- 升级到验收的条件：前端最小闭环与验证已完成
- 需要用户拍板的事项：若要继续扩大到其他页面或新增第二目标

# 本轮完成定义
- 本轮完成条件：前端最小改动完成、验证完成、文档已回写、可交验收
- 若未完成应如何交接：明确缺口后打回前端或交回预判/规则
```

## 闭环判断

这个示例里，总控层不再只输出“下一棒是前端”，而是同时给出：

- 为什么先规则再前端
- 前端具体能做什么、不能做什么
- 什么验证算通过
- 哪些文档必须回写
- 什么情况下必须停止
- 完成后为什么可以直接进入验收

这就是当前 `five-role-orchestrator` 从“总控调度骨架”升级到“轻量 harness”后的最小闭环形态。
