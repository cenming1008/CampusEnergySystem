# 后端容量基线指南

> 用于在试点前后形成第一版可复用的性能基线，避免只凭感觉判断“系统能扛多少”。

---

## 1. 目标

建议先覆盖 3 条链路：

- `GET /health/live`
- `POST /auth/login`
- `GET /health`（携带登录态）

这 3 条链路分别代表：

- 基础 HTTP 存活能力
- 认证热点能力
- 受保护接口的基础响应能力

---

## 2. 推荐执行方式

优先使用统一脚本：

```bash
bash ./scripts/shell/load_baseline.sh
```

如果要连同认证链路一起跑：

```bash
LOAD_USERNAME=admin \
LOAD_PASSWORD='your-password' \
bash ./scripts/shell/load_baseline.sh
```

默认输出到：

```text
artifacts/load/<timestamp>/
```

现在会同时生成：

- 原始 JSON 报告
- 对应 Markdown 验收摘要
- `summary.md` 汇总

---

## 3. 常用调参

```bash
BASE_URL=http://127.0.0.1:8088 \
LOAD_WORKERS=30 \
LOAD_DURATION_SECONDS=120 \
bash ./scripts/shell/load_baseline.sh
```

也可以直接覆盖验收阈值：

```bash
HEALTH_LIVE_MIN_RPS=50 \
HEALTH_LIVE_MAX_P95_MS=150 \
AUTH_LOGIN_MIN_SUCCESS_RATE=99.5 \
bash ./scripts/shell/load_baseline.sh
```

---

## 4. 首版验收建议

试点阶段建议先用下面这条简单基线作为红线：

- `health/live` 成功率 `>= 99.9%`
- `health/live` p95 `< 200ms`
- `auth/login` 成功率 `>= 99%`
- `auth/login` p95 `< 500ms`
- 过程中后端无持续 5xx、无明显重启、无数据库连接池打满

如果现场网络抖动较大，可以把认证链路阈值适当放宽，但不要放宽成功率。

---

## 5. 执行前检查

- 后端服务已启动
- 数据库、Redis、MQTT 已处于健康状态
- 测试账号已准备好
- 告警通道已静音或已知会值守人员，避免压测期间误报

---

## 6. 执行后要记录什么

每次基线至少记录：

- 时间
- 代码版本
- 服务部署方式
- 并发数和时长
- 成功率
- p50 / p95 / p99
- 压测期间 CPU、内存、数据库连接数
- 是否出现错误日志、超时或重启

建议把 JSON 报告和 Grafana 截图一起归档。
