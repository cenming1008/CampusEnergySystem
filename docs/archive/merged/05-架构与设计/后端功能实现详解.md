## 1️⃣ 用户登录

### 功能说明
用户输入用户名和密码，系统验证后返回访问令牌（Token）

### 前端入口
```
POST /auth/login
请求体: { username: "admin", password: "password" }
```

### 后端文件调用链

| 文件路径 | 文件作用 | 关键函数/类 |
|---------|---------|-----------|
| `app/api/endpoints/auth.py` | 登录接口入口 | `login()` 函数 |
| `app/core/security.py` | 密码验证和Token生成 | `verify_password()`, `create_access_token()` |
| `app/core/database.py` | 数据库连接管理 | `get_session()` |
| `app/models/tables.py` | 数据表定义 | `User` 类 |

### 数据库表
- **user** 表 - 存储用户信息（用户名、密码哈希）

### 执行流程

```
第1步: 前端发送登录请求
      ↓
第2步: auth.py 的 login() 函数接收请求
      ↓
第3步: 从数据库查询用户记录
      SQL: SELECT * FROM user WHERE username = '输入的用户名'
      ↓
第4步: 如果用户不存在 → 返回 401 错误 "用户名或密码错误"
      ↓
第5步: 如果用户存在 → 调用 security.py 的 verify_password()
      比对用户输入的密码和数据库中的密码哈希
      ↓
第6步: 如果密码错误 → 返回 401 错误 "用户名或密码错误"
      ↓
第7步: 如果密码正确 → 调用 security.py 的 create_access_token()
      生成一个有效期为5小时的JWT令牌
      ↓
第8步: 返回Token给前端
      { access_token: "eyJhbGc...", token_type: "bearer" }
```

### 返回结果
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer"
}
```

## 2️⃣ 创建设备

### 功能说明
在系统中添加一个新设备，系统会根据设备类型自动配置能源类型、单位等信息

### 前端入口
```
POST /devices/
请求头: Authorization: Bearer {token}
请求体: {
  name: "1号水表",
  sn: "WATER001",
  device_type: "water_meter"
}
```

### 后端文件调用链

| 文件路径 | 文件作用 | 关键函数/类 |
|---------|---------|-----------|
| `app/api/endpoints/devices.py` | 设备管理接口入口 | `create_device_smart()` 函数 |
| `app/api/deps.py` | Token验证 | `get_current_user()` 函数 |
| `app/services/device_service.py` | 设备业务逻辑处理 | `DeviceService.create_device_smart()` |
| `app/core/device_registry.py` | 设备类型配置库 | `device_registry.get()` |
| `app/core/database.py` | 数据库连接 | `get_session()` |
| `app/models/tables.py` | 数据表定义 | `Device` 类 |

### 数据库表
- **device** 表 - 存储设备信息（名称、序列号、类型、能源类型等）

### 执行流程

```
第1步: 前端发送创建设备请求（带Token）
      ↓
第2步: deps.py 验证Token是否有效
      - 如果Token无效 → 返回 401 错误 "未授权"
      - 如果Token有效 → 继续
      ↓
第3步: devices.py 接收请求，提取设备信息
      name = "1号水表"
      sn = "WATER001"
      device_type = "water_meter"
      ↓
第4步: 调用 DeviceService.create_device_smart()
      ↓
第5步: 从 device_registry 获取设备类型配置
      device_registry.get("water_meter") 返回：
      {
        category: "water_meter",
        energy_type: "water",
        unit: "m³/h",
        default_capacity: 50.0
      }
      ↓
第6步: 检查序列号是否重复
      SQL: SELECT * FROM device WHERE sn = 'WATER001'
      - 如果已存在 → 返回现有设备（避免重复）
      - 如果不存在 → 继续
      ↓
第7步: 自动填充设备信息
      - device_category = "water_meter"（从配置自动填充）
      - energy_type = "water"（从配置自动填充）
      - unit = "m³/h"（从配置自动填充）
      - rated_capacity = 50.0（从配置自动填充）
      ↓
第8步: 插入数据库
      SQL: INSERT INTO device (name, sn, device_type, device_category, 
           energy_type, unit, rated_capacity, is_active, created_at)
           VALUES ('1号水表', 'WATER001', 'water_meter', 'water_meter',
           'water', 'm³/h', 50.0, true, now())
      ↓
第9步: 返回创建的设备信息给前端
```

### 返回结果
```json
{
  "id": 1,
  "name": "1号水表",
  "sn": "WATER001",
  "device_type": "water_meter",
  "device_category": "water_meter",
  "energy_type": "water",
  "unit": "m³/h",
  "rated_capacity": 50.0,
  "is_active": true,
  "created_at": "2026-01-24T10:30:00"
}
```

## 3️⃣ 设备数据上报

### 功能说明
设备或系统上报能源消耗数据（电、水、气等），系统自动保存数据并计算碳排放

### 前端入口
```
POST /devices/{device_id}/data
请求头: Authorization: Bearer {token}
请求体: {
  consumption: 100.5,     // 累计消耗量
  flow_rate: 2.3,         // 瞬时流量
  voltage: 220,           // 电压（电力设备）
  current: 15.5,          // 电流（电力设备）
  pressure: 0.3           // 压力（水/气设备）
}
```

### 后端文件调用链

| 文件路径 | 文件作用 | 关键函数/类 |
|---------|---------|-----------|
| `app/api/endpoints/devices.py` | 数据上报接口 | `report_device_data()` 函数 |
| `app/services/device_service.py` | 设备数据处理 | `DeviceService.report_device_data()` |
| `app/services/energy_service.py` | 能源数据保存和碳排放计算 | `EnergyService.save_energy_data()` |
| `app/core/database.py` | 数据库连接 | `get_session()` |
| `app/models/tables.py` | 数据表定义 | `Device`, `EnergyData`, `CarbonEmission` |

### 数据库表
- **device** 表 - 读取设备信息（获取设备类型、能源类型）
- **energydata** 表 - 写入能源数据（时序数据）
- **carbon_emission** 表 - 写入碳排放数据（自动计算）

### 执行流程

```
第1步: 前端发送数据上报请求
      POST /devices/1/data
      数据: { consumption: 100.5, voltage: 220, current: 15.5 }
      ↓
第2步: devices.py 接收请求
      ↓
第3步: 调用 DeviceService.report_device_data(device_id=1, data={...})
      ↓
第4步: 从数据库获取设备信息
      SQL: SELECT * FROM device WHERE id = 1
      返回: { id: 1, device_type: "load", energy_type: "electricity" }
      ↓
第5步: 从 device_registry 获取设备配置，验证必需字段
      配置要求: ["consumption", "power"] 是必需的
      检查: data 中是否包含这些字段
      ↓
第6步: 调用 EnergyService.save_energy_data()
      参数:
      - device_id = 1
      - energy_type = "electricity"
      - consumption = 100.5
      - flow_rate = 50.2（从 power 字段）
      - voltage = 220
      - current = 15.5
      ↓
第7步: 插入能源数据到 energydata 表
      SQL: INSERT INTO energydata 
           (device_id, timestamp, energy_type, consumption, 
            flow_rate, voltage, current)
           VALUES (1, now(), 'electricity', 100.5, 50.2, 220, 15.5)
      ↓
第8步: 自动计算碳排放
      - 获取碳排放因子: 0.5839 kg CO2/kWh（电力）
      - 计算碳排放: 100.5 × 0.5839 = 58.68 kg CO2
      ↓
第9步: 插入碳排放数据到 carbon_emission 表
      SQL: INSERT INTO carbon_emission
           (device_id, timestamp, energy_type, energy_consumption,
            carbon_factor, carbon_emission)
           VALUES (1, now(), 'electricity', 100.5, 0.5839, 58.68)
      ↓
第10步: 返回保存的能源数据记录
```

### 返回结果
```json
{
  "device_id": 1,
  "timestamp": "2026-01-24T10:35:00",
  "energy_type": "electricity",
  "consumption": 100.5,
  "flow_rate": 50.2,
  "voltage": 220,
  "current": 15.5
}
```

## 4️⃣ MQTT消息处理（IoT设备数据自动上报）

### 功能说明
IoT设备通过MQTT协议发送数据，后端自动接收、解析、存储，并推送到前端

### 数据来源
```
IoT设备 → MQTT Broker → 后端监听程序
主题: mine/device/{设备编号}/telemetry
消息: {
  device_code: "001",
  voltage: 220,
  current: 15.5,
  power: 50.2,
  energy: 100.5
}
```

### 后端文件调用链

| 文件路径 | 文件作用 | 关键函数/类 |
|---------|---------|-----------|
| `app/main.py` | 应用启动时启动MQTT监听 | `start_mqtt_background()` |
| `app/services/mqtt_worker.py` | MQTT消息监听和处理 | `process_data()` |
| `app/services/device_service.py` | 设备数据处理 | `DeviceService.report_device_data()` |
| `app/services/alarm_service.py` | 报警检测 | `AlarmService.check_and_create_alarm()` |
| `app/core/socket_manager.py` | WebSocket广播管理 | `manager.broadcast()` |
| `app/models/tables.py` | 数据表定义 | `Device`, `EnergyData`, `Alarm` |

### 数据库表
- **device** 表 - 根据设备编号查询设备ID
- **energydata** 表 - 写入能源数据
- **carbon_emission** 表 - 写入碳排放数据
- **alarm** 表 - 如果触发报警，写入报警记录

### 执行流程

```
第1步: 应用启动时（main.py）
      调用 start_mqtt_background() 启动MQTT后台监听线程
      订阅主题: mine/device/+/telemetry
      ↓
第2步: IoT设备发送MQTT消息
      主题: mine/device/001/telemetry
      消息: { device_code: "001", voltage: 220, current: 15.5, ... }
      ↓
第3步: MQTT Broker 收到消息，推送给后端监听程序
      ↓
第4步: mqtt_worker.py 的 process_data() 函数被触发
      ↓
第5步: 解析JSON消息
      提取: device_code = "001"
      ↓
第6步: 根据 device_code 查询数据库获取 device_id
      SQL: SELECT id FROM device WHERE sn = '001'
      返回: device_id = 1
      ↓
第7步: 构建数据字典
      data = {
        consumption: 100.5,
        power: 50.2,
        voltage: 220,
        current: 15.5
      }
      ↓
第8步: 调用 DeviceService.report_device_data()
      将数据保存到 energydata 表
      自动计算碳排放保存到 carbon_emission 表
      ↓
第9步: 调用 AlarmService.check_and_create_alarm()
      加载报警阈值配置（config/settings.json）
      检查电流是否超限（例如：> 45A）
      检查电压是否异常（例如：< 190V 或 > 250V）
      如果触发报警 → 插入 alarm 表
      ↓
第10步: 通过 WebSocket 广播消息给所有在线前端
      manager.broadcast({
        type: "telemetry_update",
        data: { device_id: 1, voltage: 220, ... }
      })
      ↓
第11步: 前端接收WebSocket消息，实时更新界面
```

### 报警触发示例

**电流过载报警**：
```
条件: current > 45A（默认阈值）
动作: INSERT INTO alarm (device_id, message, timestamp)
      VALUES (1, '⚠️ 过载报警! 当前: 48.5A (上限: 45A)', now())
```

**电压异常报警**：
```
条件: voltage < 190V 或 voltage > 250V
动作: INSERT INTO alarm (device_id, message, timestamp)
      VALUES (1, '⚡ 电压异常! 读数: 180V (范围: 190-250V)', now())
```

## 5️⃣ 创建位置

### 功能说明
创建一个物理位置节点（如：楼栋、单元、房间），支持层级结构

### 前端入口
```
POST /locations/
请求体: {
  name: "A栋",
  location_type: "building",
  parent_id: null  // null表示顶级位置
}
```

### 后端文件调用链

| 文件路径 | 文件作用 | 关键函数/类 |
|---------|---------|-----------|
| `app/api/endpoints/locations.py` | 位置管理接口 | `create_location()` 函数 |
| `app/services/location_service.py` | 位置业务逻辑 | `LocationService.create_location()` |
| `app/models/tables.py` | 数据表定义 | `Location` 类 |

### 数据库表
- **location** 表 - 存储位置信息（支持树形结构）

### 执行流程

```
场景1: 创建顶级位置（楼栋）
─────────────────────────────
第1步: 前端发送请求
      { name: "A栋", location_type: "building", parent_id: null }
      ↓
第2步: LocationService.create_location() 接收参数
      ↓
第3步: 验证位置类型是否合法
      有效类型: building, unit, floor, room, workshop, area, zone
      ↓
第4步: 因为 parent_id = null（顶级位置）
      计算层级: level = 0
      计算路径: full_path = "/A栋"
      ↓
第5步: 插入数据库
      SQL: INSERT INTO location 
           (name, location_type, parent_id, level, full_path)
           VALUES ('A栋', 'building', NULL, 0, '/A栋')
      ↓
第6步: 返回创建的位置
      { id: 1, name: "A栋", level: 0, full_path: "/A栋" }

场景2: 创建子位置（单元）
─────────────────────────────
第1步: 前端发送请求
      { name: "3单元", location_type: "unit", parent_id: 1 }
      ↓
第2步: 验证父位置是否存在
      SQL: SELECT * FROM location WHERE id = 1
      返回: { id: 1, name: "A栋", level: 0, full_path: "/A栋" }
      ↓
第3步: 计算子位置的层级和路径
      level = 父位置的level + 1 = 0 + 1 = 1
      full_path = 父位置的full_path + "/" + 当前名称
                = "/A栋" + "/" + "3单元"
                = "/A栋/3单元"
      ↓
第4步: 插入数据库
      SQL: INSERT INTO location
           (name, location_type, parent_id, level, full_path)
           VALUES ('3单元', 'unit', 1, 1, '/A栋/3单元')
      ↓
第5步: 返回创建的位置
      { id: 2, name: "3单元", parent_id: 1, level: 1, full_path: "/A栋/3单元" }

场景3: 创建三级位置（房间）
─────────────────────────────
第1步: { name: "1309", location_type: "room", parent_id: 2 }
      ↓
第2步: 查询父位置
      返回: { id: 2, name: "3单元", level: 1, full_path: "/A栋/3单元" }
      ↓
第3步: 计算
      level = 2
      full_path = "/A栋/3单元/1309"
      ↓
第4步: 插入数据库
      { id: 3, name: "1309", parent_id: 2, level: 2, full_path: "/A栋/3单元/1309" }
```

### 位置树形结构示例
```
location 表的数据:
┌────┬────────┬──────────────┬───────────┬───────┬──────────────────┐
│ id │  name  │ location_type│ parent_id │ level │    full_path     │
├────┼────────┼──────────────┼───────────┼───────┼──────────────────┤
│ 1  │ A栋    │ building     │ NULL      │ 0     │ /A栋             │
│ 2  │ 3单元  │ unit         │ 1         │ 1     │ /A栋/3单元       │
│ 3  │ 1309   │ room         │ 2         │ 2     │ /A栋/3单元/1309  │
└────┴────────┴──────────────┴───────────┴───────┴──────────────────┘
```

## 6️⃣ 设备分组管理

### 功能说明
将多个设备组织成一个分组，便于批量管理（如：生产线A、办公区设备）

### 前端入口
```
步骤1: 创建分组
POST /device-groups/
{ name: "生产线A", group_type: "production" }

步骤2: 添加设备到分组
POST /device-groups/1/devices
{ device_ids: [1, 2, 3] }
```

### 后端文件调用链

| 文件路径 | 文件作用 | 关键函数/类 |
|---------|---------|-----------|
| `app/api/endpoints/device_groups.py` | 分组管理接口 | `create_group()`, `add_devices_to_group()` |
| `app/services/device_group_service.py` | 分组业务逻辑 | `DeviceGroupService` |
| `app/models/tables.py` | 数据表定义 | `DeviceGroup`, `DeviceGroupMembership` |

### 数据库表
- **device_group** 表 - 存储分组信息
- **device_group_membership** 表 - 存储设备和分组的多对多关系
- **device** 表 - 验证设备是否存在

### 执行流程

```
步骤1: 创建分组
─────────────────────────────
第1步: 前端发送创建分组请求
      { name: "生产线A", group_type: "production" }
      ↓
第2步: DeviceGroupService.create_group() 处理
      ↓
第3步: 插入 device_group 表
      SQL: INSERT INTO device_group (name, group_type, is_active)
           VALUES ('生产线A', 'production', true)
      ↓
第4步: 返回分组信息
      { id: 1, name: "生产线A", group_type: "production" }

步骤2: 添加设备到分组
─────────────────────────────
第1步: 前端发送请求
      POST /device-groups/1/devices
      { device_ids: [1, 2, 3] }
      ↓
第2步: DeviceGroupService.batch_add_devices_to_group() 处理
      ↓
第3步: 验证分组是否存在
      SQL: SELECT * FROM device_group WHERE id = 1
      ↓
第4步: 遍历每个设备ID
      for device_id in [1, 2, 3]:
      
      4.1: 验证设备是否存在
           SQL: SELECT * FROM device WHERE id = device_id
      
      4.2: 检查设备是否已在分组中
           SQL: SELECT * FROM device_group_membership
                WHERE device_id = device_id AND group_id = 1
           - 如果已存在 → 跳过
           - 如果不存在 → 继续
      
      4.3: 创建关联记录
           SQL: INSERT INTO device_group_membership
                (device_id, group_id, joined_at)
                VALUES (device_id, 1, now())
      ↓
第5步: 返回成功添加的数量
      { count: 3, message: "成功添加3个设备" }

查询分组中的设备
─────────────────────────────
GET /device-groups/1/devices

SQL查询:
SELECT device.* 
FROM device
JOIN device_group_membership 
  ON device.id = device_group_membership.device_id
WHERE device_group_membership.group_id = 1
ORDER BY device.id
```

### 数据库表关系
```
device_group 表（分组）
┌────┬────────────┬──────────────┐
│ id │    name    │  group_type  │
├────┼────────────┼──────────────┤
│ 1  │ 生产线A    │ production   │
└────┴────────────┴──────────────┘

device 表（设备）
┌────┬──────────┬────┐
│ id │   name   │ sn │
├────┼──────────┼────┤
│ 1  │ 1号水表  │001 │
│ 2  │ 2号电表  │002 │
│ 3  │ 3号气表  │003 │
└────┴──────────┴────┘

device_group_membership 表（多对多关联）
┌───────────┬──────────┬─────────────────────┐
│ device_id │ group_id │     joined_at       │
├───────────┼──────────┼─────────────────────┤
│ 1         │ 1        │ 2026-01-24 10:00:00 │
│ 2         │ 1        │ 2026-01-24 10:00:01 │
│ 3         │ 1        │ 2026-01-24 10:00:02 │
└───────────┴──────────┴─────────────────────┘
```

## 7️⃣ 维护记录管理

### 功能说明
记录和管理设备的维护计划、维护过程和维护结果

### 前端入口
```
步骤1: 创建维护计划
POST /maintenance/
{
  device_id: 1,
  maintenance_type: "routine",
  scheduled_time: "2026-02-01T09:00:00",
  title: "例行维护",
  operator: "张三"
}

步骤2: 开始维护
POST /maintenance/100/start

步骤3: 完成维护
POST /maintenance/100/complete
{
  result: "维护完成，设备正常",
  cost: 500
}
```

### 后端文件调用链

| 文件路径 | 文件作用 | 关键函数/类 |
|---------|---------|-----------|
| `app/api/endpoints/maintenance.py` | 维护管理接口 | 各种维护操作函数 |
| `app/services/maintenance_service.py` | 维护业务逻辑 | `MaintenanceService` |
| `app/models/tables.py` | 数据表定义 | `DeviceMaintenance` |

### 数据库表
- **device_maintenance** 表 - 存储维护记录
- **device** 表 - 验证设备是否存在

### 执行流程

```
步骤1: 创建维护计划
─────────────────────────────
第1步: 前端发送创建维护计划请求
      {
        device_id: 1,
        maintenance_type: "routine",
        scheduled_time: "2026-02-01 09:00:00",
        title: "例行维护"
      }
      ↓
第2步: MaintenanceService.create_maintenance() 处理
      ↓
第3步: 验证设备是否存在
      SQL: SELECT * FROM device WHERE id = 1
      ↓
第4步: 验证维护类型是否合法
      有效类型: routine（例行）, repair（维修）, inspection（巡检）,
               upgrade（升级）, calibration（校准）
      ↓
第5步: 插入 device_maintenance 表
      SQL: INSERT INTO device_maintenance
           (device_id, maintenance_type, scheduled_time, title,
            operator, status, created_at)
           VALUES (1, 'routine', '2026-02-01 09:00:00', '例行维护',
                   '张三', 'scheduled', now())
      ↓
第6步: 返回维护记录
      { id: 100, device_id: 1, status: "scheduled", ... }

步骤2: 开始维护
─────────────────────────────
第1步: POST /maintenance/100/start
      ↓
第2步: MaintenanceService.start_maintenance() 处理
      ↓
第3步: 更新维护记录状态
      SQL: UPDATE device_maintenance
           SET status = 'in_progress',
               actual_start_time = now()
           WHERE id = 100
      ↓
第4步: 返回更新后的记录
      { id: 100, status: "in_progress", actual_start_time: "2026-02-01 09:05:00" }

步骤3: 完成维护
─────────────────────────────
第1步: POST /maintenance/100/complete
      { result: "维护完成，设备正常", cost: 500 }
      ↓
第2步: MaintenanceService.complete_maintenance() 处理
      ↓
第3步: 查询维护记录，获取开始时间
      SQL: SELECT actual_start_time FROM device_maintenance WHERE id = 100
      返回: actual_start_time = "2026-02-01 09:05:00"
      ↓
第4步: 计算维护时长
      duration = now() - actual_start_time
               = "2026-02-01 11:05:00" - "2026-02-01 09:05:00"
               = 120分钟
      ↓
第5步: 更新维护记录
      SQL: UPDATE device_maintenance
           SET status = 'completed',
               actual_end_time = now(),
               duration_minutes = 120,
               result = '维护完成，设备正常',
               cost = 500
           WHERE id = 100
      ↓
第6步: 返回完成的记录
      {
        id: 100,
        status: "completed",
        duration_minutes: 120,
        cost: 500
      }
```

### 维护状态流转
```
scheduled（已计划）
    ↓ [开始维护]
in_progress（进行中）
    ↓ [完成维护]
completed（已完成）

或者：
scheduled（已计划）
    ↓ [取消维护]
cancelled（已取消）
```

|-----|---------|---------|

| 碳排放汇总 | `app/services/energy_service.py` | `get_carbon_summary()` |

### 8.1 查询设备历史数据流程

```
第1步: 前端发送请求
      GET /devices/1/data?start_time=2026-01-01&end_time=2026-01-24
      ↓
第2步: DeviceService.get_device_data() 处理
      ↓
第3步: 获取设备信息
      SQL: SELECT * FROM device WHERE id = 1
      返回: { energy_type: "electricity" }
      ↓
第4步: 调用 EnergyService.get_energy_data()
      ↓
第5步: 查询 energydata 表
      SQL: SELECT * FROM energydata
           WHERE device_id = 1
             AND energy_type = 'electricity'
             AND timestamp >= '2026-01-01'
             AND timestamp <= '2026-01-24'
           ORDER BY timestamp DESC
           LIMIT 1000
      ↓
第6步: 返回数据列表
      [
        { device_id: 1, timestamp: "2026-01-24 10:00", consumption: 100.5, ... },
        { device_id: 1, timestamp: "2026-01-24 09:00", consumption: 95.2, ... },
        ...
      ]
```

### 8.2 统计数据计算流程

```
第1步: 前端请求统计数据
      GET /devices/1/statistics?start_time=2026-01-01&end_time=2026-01-24
      ↓
第2步: EnergyService.calculate_statistics() 处理
      ↓
第3步: 查询时间范围内的所有数据
      SQL: SELECT * FROM energydata
           WHERE device_id = 1
             AND energy_type = 'electricity'
             AND timestamp BETWEEN '2026-01-01' AND '2026-01-24'
      ↓
第4步: 在内存中计算统计值
      total_consumption = SUM(所有记录的consumption)
                        = 100.5 + 95.2 + ... = 2450.8
      
      avg_consumption = total_consumption / 记录数
                      = 2450.8 / 24 = 102.1
      
      avg_flow_rate = SUM(所有flow_rate) / 记录数
                    = 50.2 + 48.5 + ... / 24 = 49.8
      
      peak_flow_rate = MAX(所有flow_rate)
                     = 55.6
      ↓
第5步: 返回统计结果
      {
        total_consumption: 2450.8,
        avg_consumption: 102.1,
        avg_flow_rate: 49.8,
        peak_flow_rate: 55.6,
        data_count: 24
      }
```

### 8.3 碳排放汇总流程

```
第1步: 前端请求碳排放汇总

      ↓
第3步: 按能源类型分组统计

                  SUM(carbon_emission) as total_emission,
                  SUM(energy_consumption) as total_consumption
           FROM carbon_emission
           WHERE timestamp BETWEEN '2026-01-01' AND '2026-01-24'
           GROUP BY energy_type
      ↓
第4步: 数据库返回分组统计结果
      [
        { energy_type: "electricity", total_emission: 1458.6, total_consumption: 2500 },
        { energy_type: "water", total_emission: 83.5, total_consumption: 500 },
        { energy_type: "gas", total_emission: 216.2, total_consumption: 100 }
      ]
      ↓
第5步: 格式化返回结果
      {
        total_carbon: 1758.3,  // 总碳排放
        by_energy_type: {
          electricity: {
            carbon_emission: 1458.6,
            energy_consumption: 2500,
            unit: "kWh"
          },
          water: {
            carbon_emission: 83.5,
            energy_consumption: 500,
            unit: "m³"
          },
          gas: {
            carbon_emission: 216.2,
            energy_consumption: 100,
            unit: "m³"
          }
        }
      }
```

## 9️⃣ 前端实时数据推送（WebSocket）

### 功能说明
通过WebSocket协议，后端将设备数据实时推送到前端，前端无需轮询

### 技术流程

```
第1步: 前端打开WebSocket连接
      前端代码: const ws = new WebSocket('ws://localhost:8088/ws')
      ↓
第2步: 后端 main.py 的 websocket_endpoint() 接收连接
      ↓
第3步: ConnectionManager 管理器接受连接
      - 执行: await websocket.accept()
      - 将连接添加到 active_connections 列表
      - 记录日志: "✅ WebSocket 客户端已连接，当前连接数: 1"
      ↓
第4步: 连接保持活跃状态，等待消息推送
      ↓
第5步: 当有MQTT消息到达时
      mqtt_worker.py 处理完数据后
      调用 mqtt_to_ws_callback() 回调函数
      ↓
第6步: mqtt_to_ws_callback() 调度异步任务
      使用 asyncio.run_coroutine_threadsafe() 跨线程调度
      将 manager.broadcast() 添加到事件循环
      ↓
第7步: ConnectionManager.broadcast() 执行
      遍历所有活跃连接
      for connection in active_connections:
          await connection.send_json({
              type: "telemetry_update",
              data: { device_id: 1, voltage: 220, ... }
          })
      ↓
第8步: 前端WebSocket接收消息
      前端代码: ws.onmessage = (event) => {
          const message = JSON.parse(event.data)
          // 更新界面显示
          updateDeviceDisplay(message.data)
      }
      ↓
第9步: 前端界面实时更新，显示最新数据
```

### 涉及的文件

| 文件路径 | 作用 |
|---------|------|
| `app/main.py` | WebSocket端点定义 |
| `app/core/socket_manager.py` | 连接管理和消息广播 |
| `app/services/mqtt_worker.py` | MQTT消息处理和WebSocket回调 |
| `frontend/src/stores/useSocketStore.ts` | 前端WebSocket状态管理 |

## 🔟 定时任务（自动训练和预测）

### 功能说明
系统自动在后台执行定时任务，如LSTM模型训练、负荷预测更新等

### 涉及的文件

| 文件路径 | 作用 |
|---------|------|
| `app/main.py` | 启动时启动调度器 |
| `app/services/scheduler_service.py` | 定时任务管理 |
| `app/services/forecast_adapter.py` | 预测功能实现 |
| `lstm_forecast/` | LSTM模型训练和预测 |

### 定时任务流程

```
应用启动
↓
main.py 的 lifespan startup 阶段
↓
调用 start_scheduler() 启动定时任务调度器
↓
创建 BackgroundScheduler
↓
添加定时任务

任务1: LSTM模型自动训练
  触发时间: 每天凌晨2点
  执行函数: auto_train_lstm_models()
  流程:
    1. 训练系统级负荷预测模型
    2. 训练各设备的负荷预测模型
    3. 训练风光预测模型
  涉及数据: 从 energydata 表读取历史数据（60天）

任务2: 预测数据自动更新
  触发时间: 每小时执行一次
  执行函数: auto_update_forecasts()
  流程:
    1. 更新系统负荷预测（未来24小时）
    2. 更新各设备预测
    3. 保存预测结果到 prediction 表
```

### LSTM训练任务详细流程

```
第1步: 时间到达凌晨2点，调度器触发
      ↓
第2步: auto_train_lstm_models() 函数执行
      ↓
第3步: 创建 ForecastAdapter 实例
      ↓
第4步: 训练系统级负荷预测模型
      4.1: 从 energydata 表读取60天历史数据
           SQL: SELECT * FROM energydata
                WHERE energy_type = 'electricity'
                  AND timestamp >= now() - interval '60 days'
                ORDER BY timestamp
      
      4.2: 数据预处理
           - 按小时聚合数据
           - 归一化处理（缩放到0-1范围）
           - 构造训练序列（24小时为一个输入序列）
      
      4.3: 调用 lstm_forecast 模块训练模型
           - 创建LSTM神经网络（2层，64和32个单元）
           - 训练50个epoch
           - 保存模型到 lstm_forecast/models/
      
      4.4: 记录日志: "系统负荷预测模型训练完成"
      ↓
第5步: 对每个活跃设备训练模型
      5.1: 查询所有活跃设备
           SQL: SELECT * FROM device WHERE is_active = true
      
      5.2: 遍历每个设备
           for device in devices:
               - 读取该设备的历史数据
               - 训练专属预测模型
               - 保存模型文件
      ↓
第6步: 训练完成，等待下次触发
```
