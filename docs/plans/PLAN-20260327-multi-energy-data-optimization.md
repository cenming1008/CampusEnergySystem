# PLAN-20260327-multi-energy-data-optimization

## 1. 背景与问题

基于探索线程已沉淀的 [PLAN-20260327-multi-energy-data-audit.md](/Users/todo/MineEnergySystem/docs/plans/PLAN-20260327-multi-energy-data-audit.md)，当前项目在 `电 / 热 / 气 / 冷 / 碳排放` 五类对象上，已经具备统一接入、统一存储、统一查询和统一展示能力，但多能源数据业务逻辑仍明显偏“基础 EMS 底座”，还不适合作为强业务语义、强核算口径的正式多能源系统。

探索线程已经明确指出，当前问题的核心更偏“业务语义不足”，而不是单纯技术分层问题，集中体现为：

- 多能源建模主要依赖 `energy_type`、`device_type`、`device_category` 和通用时序字段 `consumption` / `flow_rate`，能源专属业务语义不足。
- `consumption` 被定义为累计量、`flow_rate` 被定义为瞬时量，但统计、概览、碳排、分析、报表等路径并未严格保护这一边界，累计量 / 瞬时量存在混用风险。
- 当前单位体系更像“静态展示映射”，还没有形成“内部标准单位 + 入库换算 + 展示单位”的完整规则，冷 / 热 / 气存在量纲和单位混用风险。
- 碳排放逻辑本质上仍是固定因子乘法，更适合驾驶舱展示和趋势试算，不适合作为正式核算结论。
- `analysis` / `reports` 对多能源的理解仍偏通用分类与明细导出，还没有形成电 / 热 / 气 / 冷各自的第一批业务指标体系。

因此，本轮不是重写所有能源模型，而是把探索结论收敛成第一批可执行计划，先把最容易误用、最影响后续分析与报表的业务口径问题压实。

---

## 2. 目标

- 明确本轮是“第一批多能源数据业务优化”，不是全系统重构。
- 先收敛五类对象的第一批业务边界：电 / 热 / 气 / 冷 / 碳排放。
- 先明确累计量、瞬时量、差值量、统计量的使用规则，并映射到现有模型、接口和报表语义。
- 先明确内部标准单位、入库换算和展示单位规则，避免跨能源、跨量纲直接混算。
- 先明确碳排放逻辑当前是展示级还是核算级，并锁定第一批仅做到的边界。
- 先对 `analysis` / `reports` 做第一批多能源业务口径收敛，不再只停留在粗粒度 `energy_type` 分类汇总。
- 为后端线程明确最小实施面，为前端线程明确最小联调面，不需要再次讨论方案。

本轮目标不是一次补齐所有能源机理模型，而是先把后续所有实现都依赖的业务口径定清。

---

- 不做预测模型重构。

## 5. 实施步骤

### 阶段 1：多能源口径梳理

目标：
- 固定电 / 热 / 气 / 冷 / 碳排放五类对象的第一批业务边界。
- 明确累计量、瞬时量、差值量、统计量四类口径定义及禁止混用场景。

实施要点：
- 对现有 `EnergyData`、统计接口、分析接口、报表接口逐项标注“当前字段语义”和“目标业务语义”。
- 对“可直接汇总”和“必须先做差值”的字段形成明确清单。
- 若某些现有接口短期无法立即修正，先明确其仅适用于展示级或粗统计场景。

独立验收：
- 已形成多能源第一批口径清单。
- 已明确累计量 / 瞬时量禁止混用的场景。

### 阶段 2：数据模型与字段语义收敛

目标：
- 在不推翻现有统一模型的前提下，补足第一批字段语义与约束说明。

实施要点：
- 继续保留统一时序底座，但补明确字段含义、适用能源、禁止误用场景。
- 给电 / 热 / 气 / 冷补第一批“最小必备业务语义”清单。
- 如需新增最小 DTO / schema 约束，只在直接相关路径内进行。

独立验收：
- 统一模型仍保留，但字段语义边界已清楚。
- 电 / 热 / 气 / 冷第一批最小业务语义已可核对。

### 阶段 3：单位和统计口径收敛

目标：
- 建立“内部标准单位 + 入库换算 + 展示单位”的第一批统一约束。

实施要点：
- 为每类能源明确内部标准单位。
- 明确哪些单位可直接入库，哪些需要归一化换算。
- 明确统计层对累计量、瞬时量、差值量分别允许使用的聚合方式。
- 避免冷 / 热 / 气 / 电跨量纲直接混算。

独立验收：
- 单位策略已形成统一约束。
- 统计层已明确哪些字段可以直接汇总，哪些必须差值后再统计。

### 阶段 4：碳排边界收敛

目标：
- 明确当前碳排放逻辑的适用边界，并区分展示级与核算级。

实施要点：
- 先把现有碳排逻辑定位为展示级还是核算级，并写入代码注释 / 文档 / handoff。
- 明确本轮只保留哪类固定因子乘法逻辑，哪些正式核算场景本轮不支持。
- 若后端需要保留现有自动计算链路，优先加边界说明，不直接扩成复杂核算引擎。

独立验收：
- 当前碳排逻辑适用边界已明确。
- 展示级与核算级边界已写死，避免误用。

### 阶段 5：analysis / reports 第一批优化

目标：
- 让 `analysis` / `reports` 第一批不再只依赖粗粒度 `energy_type` 分类汇总。

实施要点：
- 先收敛最关键的多能源业务口径，而不是一次补齐所有能源专属指标。
- 对 `analysis` 明确哪些字段当前仅适用于电力，哪些需要改成更通用或分能源返回。
- 对 `reports` 明确哪些导出仍然只是通用明细，哪些第一批需要增加业务语义说明或字段口径区分。
- 若实现成本过高，优先加兼容层和文档说明，不扩大到报表系统整体重构。

独立验收：
- `analysis` / `reports` 已有第一批多能源口径收敛结果。
- 不再只有“按 energy_type 粗分类”的单一叙事。

### 阶段 6：验证与文档回写

目标：
- 让后端实施边界、前端联调边界和剩余风险在文档中闭环。

实施要点：
- 后端线程实施后更新本计划“进度记录”。
- 同步更新 `docs/plans/current-status.md` 和 `docs/plans/handoff.md` 中对应内容块。
- 若实施范围缩小、延期或取消，必须直接回写计划，不只留在聊天记录里。

独立验收：
- PLAN、`current-status.md`、`handoff.md` 三者口径一致。

## 6. 风险与回滚

### 风险 1：模型语义收敛成本高于预期

- 表现：仅靠字段说明无法覆盖现有实现差异，容易演变成全模型重构。
- 应对：优先保留现有底座，先补兼容层、字段语义约束和使用边界。
- 回滚边界：若某个模型调整已开始牵动大量 schema 或存量数据迁移，立即停止，保留文档约束和最小兼容改造。

### 风险 2：统计口径调整引发旧接口结果变化

- 表现：`overview`、`analysis`、`reports` 的结果与当前页面认知出现差异。
- 应对：优先保持兼容接口，必要时通过新增字段、附加说明或兼容 DTO 过渡。
- 回滚边界：若调整后导致前端现有页面不可用，优先恢复原返回，再把新口径通过新字段或新路径引入。

### 风险 3：碳排边界收敛被误解为碳核算系统重构

- 表现：后端实施时发散到因子版本管理、组织边界、核算报送等复杂领域。
- 应对：本轮只明确展示级与核算级边界，不建设完整核算引擎。
- 回滚边界：若实施已进入复杂核算设计，立即收缩回“边界标注 + 第一批适用场景”。

### 风险 4：前端提前按猜测改展示逻辑

- 表现：后端口径尚未稳定，前端先做大改版，导致联调反复。
- 应对：前端本轮只做联调准备和最小适配，不做页面大重构。
- 回滚边界：若前端已开始大改页面，优先停止页面层扩张，恢复到接口兼容联调模式。

总回滚原则：

- 若发现模型调整成本过高，优先保留兼容层，而不是扩大重构范围。
- 回滚以“口径层 / 单位层 / 碳排层 / 分析报表层”分阶段进行，不做全局推翻。
- 回滚时优先保持现有接口和页面可用，再决定后续是否继续收敛。
