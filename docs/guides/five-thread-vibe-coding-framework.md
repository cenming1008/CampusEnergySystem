# Codex 五角色 Vibe Coding 框架

> 适用于个人在 Codex 中进行高频迭代开发。本文是 [AI 多线程协作 SOP](./ai-collaboration-sop.md) 的执行层补充：SOP 管主题治理、主区维护、daily 归档与 archive 收口，本文管角色分流、边界控制、文档分级、契约承载与阶段验收。

> 兼容口径：本文正式使用“角色”作为主名；`五线程`、`线程` 仅作为历史兼容称呼保留。后续文档若出现“五线程”，默认等价理解为“五角色协作法”。

---

## 1. 方法定位

### 1.1 这套方法保留的核心优点

- 不默认五角色全开。
- 默认走“能闭环的最短路径”。
- 大多数轮次控制在 2 到 3 个角色内。
- 服务于个人持续开发，不演化为重型团队流程。
- 保留 `current-status.md`、`handoff.md`、`PLAN-*.md` 的文档治理思想。
- 验收角色只负责阶段核对与主题收口，不作为常驻实现角色。

### 1.2 本文要解决的执行问题

- “线程”命名容易与 worker、process、sub-agent 混淆。
- 探索与规范边界不清，前置角色容易互相抢活。
- 高频小轮次的主区回写成本偏高。
- 分流规则偏长，首轮判断还不够快。
- 人类拍板点偏多，影响连续推进。
- 验收定义正确，但缺少固定 checklist 和证据口径。
- 前后端并行时，契约载体不够硬。
- 缺少连续打回后的升级机制。

### 1.3 方法总原则

- 默认最短闭环，不为“可能变复杂”提前走重流程。
- 先事实判断，再边界裁决，再进入实现。
- 无接力、无边界变化、无主题变化，不动主区。
- 前后端并行前，必须先有单一契约载体。
- 每轮最小闭环结束后，必须执行一次阶段验收。
- 连续有效打回达到阈值，必须升级路径，不允许原地反弹。

## 2. 五角色定义

### 2.1 五角色总表

| 角色 | 原兼容称呼 | 核心职责 | 是否常驻 |
| --- | --- | --- | --- |
| 预判 | 探索 | 做事实判断，给最小路径 | 否 |
| 规则 | 规范 | 做边界裁决，锁口径与契约 | 否 |
| 前端实现 | 前端 | 处理页面、组件、状态、交互与前端接口消费 | 是 |
| 后端实现 | 后端 | 处理接口、schema、service、权限与返回结构 | 是 |
| 验收 | 验收 | 做阶段核对、打回判断与主题收口 | 否 |

### 2.2 预判角色

**角色定位**

- 负责事实判断：定位归属、判断最小路径、判断是否需要升级。

**进入条件**

- 根因不清楚。
- 不清楚归前端、后端还是契约问题。
- 不清楚是否属于当前主主题。
- 不清楚是否需要前后端联动。
- 连续打回后需要重新收敛路径。

**退出条件**

- 已明确当前问题归属。
- 已给出推荐路径。
- 已说明本轮非目标。
- 已判断是否需要契约、是否需要 `PLAN`、是否需要规则角色介入。

**禁止越界事项**

- 不负责长期规则制定。
- 不负责正式术语裁决。
- 不默认写长篇规范文档。
- 不把验证性修改扩成正式实现。

**最小交付物**

- 推荐路径。
- 本轮边界。
- 下一角色。
- 必要时的最小契约草案或风险说明。

### 2.3 规则角色

**角色定位**

- 负责边界裁决：锁主题、锁术语、锁范围、锁契约口径、决定是否立 `PLAN`。

**进入条件**

- 主题是否成立不明确。
- 术语、对象边界、兼容口径不稳定。
- 主区口径分裂。
- 需要决定是否建立或更新正式 `PLAN`。
- 需要裁决 breaking change、并行边界、非目标冻结范围。

**退出条件**

- 当前主题已锁定。
- 术语、对象、非目标已明确。
- 契约口径稳定。
- 实现角色可直接接手。

**禁止越界事项**

- 不回做大段根因排查。
- 不借机扩写重型治理文档。
- 不顺手做实现。
- 不发明新需求。

**最小交付物**

- 边界裁决结论。
- 稳定的契约口径或 `PLAN` 结论。
- 允许范围与禁止扩张项。

### 2.4 前端实现角色

**角色定位**

- 负责前端页面、组件、状态、路由、交互、前端接口消费的最小必要实现。

**进入条件**

- 问题已明确落在前端。
- 或接口契约已明确，可进行前端适配。

**退出条件**

- 最小改动完成。
- 已做前端最小验证。
- 若需交接，已写清接口依赖、页面影响与剩余风险。

**禁止越界事项**

- 不擅自重定义接口语义。
- 不用 UI 兼容掩盖后端契约问题。
- 不顺手改后端逻辑。
- 不在无依据情况下扩大页面重构范围。

**最小交付物**

- 前端改动。
- 最小验证结果。
- 若需交接，补前端消费说明与风险说明。

### 2.5 后端实现角色

**角色定位**

- 负责接口、schema、service、权限、字段、空值处理、状态码和返回结构的最小必要实现。

**进入条件**

- 问题已明确落在后端。
- 或契约已明确，需要提供或修正接口能力。

**退出条件**

- 最小改动完成。
- 已做后端最小验证。
- 若需交接，已写清接口改动、兼容边界、前端注意事项。

**禁止越界事项**

- 不顺手改前端页面逻辑。
- 不无依据扩大 schema 或 service 重构。
- 不默认引入 breaking change。
- 不把兼容修复升级成大改造。

**最小交付物**

- 后端改动。
- 最小验证结果。
- 若需交接，补接口样例、兼容说明与风险说明。

### 2.6 验收角色

**角色定位**

- 负责阶段核对与主题收口，给出通过、打回或收口结论。

**进入条件**

- 一轮最小闭环已完成。
- 或当前主题拟阶段完成。
- 或拟正式收口、退出主区、切下一个主题。

**退出条件**

- 已给出通过、打回或收口结论。
- 已判断证据是否充分。
- 已明确下一步是继续、返工还是切主题。

**禁止越界事项**

- 不顺手开新需求。
- 不顺手扩实现范围。
- 不在证据不足时主观判通过。
- 不替代规则角色重写边界。

**最小交付物**

- checklist 结果。
- 通过、打回或正式收口结论。
- 剩余风险或切主题建议。

## 3. 预判与规则的边界

### 3.1 只属于预判的事

- 判断问题更像前端、后端还是契约问题。
- 判断当前问题是否已有足够事实可直接实现。
- 给出最小修复路径。
- 给出最强假设和验证方向。
- 标记本轮非目标。
- 判断是否需要升级到规则角色。
- 判断是否需要前后端联动。

一句话：预判只回答“事实是什么、先走哪条路”。

### 3.2 只属于规则的事

- 判断是否升级为新主题。
- 锁定正式主题名称。
- 锁定术语、对象边界、兼容口径。
- 决定是否必须建立或更新 `PLAN`。
- 决定是否允许 breaking change。
- 决定并行边界和契约口径。
- 修改 `AGENTS.md`、`docs/guides/*`、`PLAN-*.md` 中的长期规则表达。

一句话：规则只回答“边界怎么定、口径怎么写”。

### 3.3 可直接合并为预判层的小任务

以下任务默认只启用预判层，不额外拉起规则角色：

- 局部 bug 定位。
- 单页按钮无响应排查。
- 单接口空值或字段消费排查。
- 明显属于当前主主题的局部修复。
- 不涉及新主题、不涉及术语变化、不涉及 `PLAN` 升级的联调任务。

### 3.4 避免预判与规则来回拉扯的硬规则

1. 先事实，后裁决。没有事实，不进规则。
2. 规则不回做事实排查。若缺事实，明确缺哪一项，再退回预判。
3. 同一轮最多一次 `预判 -> 规则`。规则只能做裁决，不能原样打回“再看一遍”。
4. 纯前端小修复、纯后端兼容修复、已有稳定契约的联调适配，禁止单独拉起规则角色。
5. 规则输出优先只写裁决项：主题、范围、非目标、契约、是否需要 `PLAN`、验收口径。

## 4. 30 秒分流机制

### 4.1 先问 6 个问题

1. 这件事是否明显属于当前主主题？
2. 根因是否已经清楚？
3. 是否已经明确归前端、后端或双方？
4. 是否涉及主题、术语、边界或兼容裁决？
5. 是否需要前后端共享一个稳定契约？
6. 这一轮能否由单角色直接闭环？

### 4.2 问题回答与推荐路径

| 判断结果 | 推荐路径 |
| --- | --- |
| 属于当前主主题，根因清楚，只改前端，可单轮闭环 | 前端实现 -> 验收 |
| 属于当前主主题，根因清楚，只改后端，可单轮闭环 | 后端实现 -> 验收 |
| 属于当前主主题，但根因不清或归属不清 | 预判 -> 实现 -> 验收 |
| 前后端都要改，但契约已经稳定 | 前端实现 + 后端实现 -> 验收 |
| 前后端都要改，且契约还不稳 | 预判 -> 规则或契约 -> 前后端实现 -> 验收 |
| 不确定是否属于当前主主题，或可能升级成新主题 | 预判 -> 规则 -> 判断是否立 `PLAN` |
| 只是规则、入口、文档治理 | 规则 -> 验收 |
| 已连续被有效打回两次 | 升级到重量轮：预判 -> 规则 -> `PLAN` -> 实现 -> 验收 |

### 4.3 超短版决策卡

```md
## 30 秒分流卡

先问 6 件事：
1. 属不属于当前主主题？
2. 根因清不清？
3. 归前端、后端还是双方？
4. 需不需要规则裁决？
5. 需不需要稳定契约？
6. 能不能单角色闭环？

默认规则：
- 能单角色闭环，就不要拉前置角色
- 根因不清，先走预判
- 边界不稳，才拉规则
- 前后端并行前，先有契约
- 一轮结束必须验收
- 连续两次有效打回，升级到 `PLAN` 路径
```

## 5. 文档回写分级

### 5.1 轻量轮

**适用场景**

- 纯前端小修复。
- 纯后端小修复。
- 已有稳定契约的局部联调。
- 当轮可以在同一角色内直接闭环。
- 不改变当前主题状态，不影响后续接力。

**必写文档**

- 无强制主区回写。
- 最终输出至少说明：目标、改动、验证、风险。

**可跳过文档**

- `docs/plans/current-status.md`
- `docs/plans/handoff.md`
- `PLAN-*.md`

**升级条件**

- 需要交给另一个角色继续做。
- 影响当前主主题判断。
- 影响接口契约。
- 出现打回。
- 出现边界争议。

### 5.2 标准轮

**适用场景**

- 需要角色接力。
- 当前主主题状态发生变化。
- 需要记录阻塞、待办或下一棒。
- 需要明确前后端契约，但不一定单独立 `PLAN`。
- 一轮完成后需要验收判断。

**必写文档**

- `docs/plans/current-status.md`
- `docs/plans/handoff.md`

**可跳过文档**

- `PLAN-*.md`
- `*-analysis.md`

**升级条件**

- 可能成为新主题。
- 需要正式分阶段推进。
- 涉及 breaking change 或兼容裁决。
- 契约复杂且需要多轮反复引用。
- 连续有效打回达到升级阈值。

### 5.3 重量轮

**适用场景**

- 新主题或准新主题。
- 根因复杂、周期超过一轮。
- 前后端都要改且契约复杂。
- 需要明确非目标和阶段边界。
- 需要后续多轮复用分析结果。

**必写文档**

- `docs/plans/current-status.md`
- `docs/plans/handoff.md`
- `PLAN-*.md`

**可跳过文档**

- `*-analysis.md` 不是默认必写，仅在长分析需要复用时新增。

### 5.4 主区文档的最低必要字段

`current-status.md` 最低保留 6 项：

1. 当前主主题
2. 当前阶段或当前轮目标
3. 当前路径或当前负责角色
4. 当前阻塞
5. 当前待办
6. 当前风险或当前验收结论

`handoff.md` 最低保留 5 项：

1. 下一角色
2. 下一步动作
3. 已知边界或非目标
4. 打回条件
5. 必要上下文或契约链接

### 5.5 `PLAN` 的硬触发条件

满足任一条件时，`PLAN-*.md` 必须出现：

- 新主题成立。
- 当前任务预计超过一轮。
- 前后端都要改且需要阶段拆分。
- 存在明确非目标，需要冻结范围。
- 涉及兼容、breaking change、命名迁移、契约裁决。
- 连续打回升级后，需要重新收敛路径。

### 5.6 哪些轮次默认不动主区

以下轮次默认不改主区文档：

- 单角色即可闭环的小修复。
- 不影响当前主主题状态的样式、文案、局部交互修复。
- 无后续接力的后端兼容性小修。
- 已有明确契约、当轮一次完成的前端适配。

硬规则：无接力、无边界变化、无主题变化，不动主区。

## 6. 契约先行规则

### 6.1 什么情况下必须有契约载体

满足任一项时，必须先写契约再并行或接力：

- 前后端要并行。
- 前后端要串行接力，但接口会变化。
- 返回字段、空值语义、兼容方式会变化。
- 当前任务可能因契约不稳而反复打回。

### 6.2 契约写在哪里

优先顺序如下：

1. 当前正式 `PLAN-*.md`
2. `docs/plans/handoff.md`
3. `docs/plans/current-status.md`

硬规则：

- 同一轮只允许一个主契约载体。
- 契约一旦确定，前后端实现与验收默认都以该载体为准。

### 6.3 契约最小字段

- 接口路径
- 请求参数
- 返回字段
- 空值与异常处理约定
- 兼容边界
- 前端消费方式
- 非目标

## 7. 人类拍板点最小化

以下节点必须由人类拍板：

1. 是否新开主题。
2. 是否升级为正式 `PLAN-*.md`。
3. 是否接受 breaking change。
4. 是否接受范围扩大为第二个主动作。
5. 是否把阶段验收升级为正式收口验收。
6. 是否把主题迁入 `docs/archive/plans/`。

以下节点默认不需要人工拍板：

- 当前主题内的局部前端修复还是局部后端修复。
- 是否跳过规则角色处理低风险局部问题。
- 已在正式 `PLAN` 范围内的兼容修正。
- daily 归档执行本身。

## 8. 验收机制

### 8.1 阶段验收 checklist

每轮最小闭环结束后，至少核对以下事项：

- 本轮目标是否已完成。
- 改动是否仍在既定边界内。
- 是否做了最小必要验证。
- 验证结果是否足以支撑“暂时通过”。
- 是否仍存在阻塞下一轮的关键风险。
- 是否需要交给下一角色。
- 是否需要回写主区或更新契约。

阶段验收输出只能是三种：

- 通过：进入下一轮或待收口
- 打回：回到指定角色补缺口
- 升级：进入重量轮治理

### 8.2 正式收口验收 checklist

主题拟阶段收口、正式收口、退出主区、切下一个主题时，额外核对：

- 当前主题目标是否达到阶段完成或正式完成。
- 是否还有明确且独立的下一轮最小范围。
- 当前遗留项是否仍值得保留为主主题。
- `current-status.md` 与 `handoff.md` 是否已更新为收口状态。
- 是否需要保留 `PLAN`。
- 是否需要 daily 归档。
- 是否需要迁 archive。
- 是否需要切换下一个主主题。

正式收口输出只能是三种：

- 阶段收口
- 正式收口
- 暂不收口，继续当前主题

### 8.3 打回条件

出现以下任一项，验收必须打回：

- 本轮目标未完成。
- 改动超出既定边界。
- 无最小验证，或验证不足以支撑结论。
- 契约已变化但未记录。
- 仍存在关键阻塞却被当作已完成。
- 证据不足以判断是否通过。

### 8.4 证据要求

**前端任务至少提供其一**

- 构建、lint 或测试结果
- 页面截图或交互结果描述
- 关键状态链路说明

**后端任务至少提供其一**

- 测试结果
- 接口样例
- 日志、状态码或返回结构说明

**联动任务至少提供其二**

- 接口契约样例
- 前端消费结果
- 后端验证结果
- 风险说明

**收口任务额外必须提供**

- 当前剩余风险
- 是否还有下一轮最小范围
- 是否建议切主题或归档

### 8.5 验收角色禁止扩任务的场景

以下情况下，验收角色只记录候选项，不把它们混入当前通过条件：

- 当前轮只是局部修复。
- 当前目标已明确完成。
- 新想法不影响本轮是否通过。
- 新风险属于后续优化而非本轮缺陷。
- 新主题尚未正式立项。

## 9. 连续打回升级机制

### 9.1 什么叫一次有效打回

只有同时满足以下条件，才算一次有效打回：

- 明确指出接收角色。
- 明确指出打回原因。
- 明确指出缺失项或错误项。
- 明确指出补完后如何重新验收。

### 9.2 升级阈值

- 同一问题链路中，连续 2 次有效打回：必须升级。
- 同一问题链路中，累计 3 次有效打回：禁止继续原路径，必须走重量轮。

### 9.3 升级后的固定路径

默认升级到：

`预判 -> 规则 -> PLAN/契约 -> 实现 -> 验收`

升级动作必须补齐三件事：

1. 重新写明问题归属。
2. 重新锁定边界与非目标。
3. 明确新的验收口径。

### 9.4 谁负责重新收敛

- 事实一直不清：由预判角色重新收敛。
- 边界一直不稳：由规则角色重新收敛。
- 契约反复变：由规则角色先锁契约，再交实现。
- 实现未按契约做：直接回对应实现角色，不重新开判。

硬规则：升级后必须指定唯一收敛责任角色。

## 10. 单轮最小闭环

一轮最小闭环至少包含：

1. 确认当前主题与任务路径。
2. 必要时完成预判或规则裁决。
3. 完成一段最小实现。
4. 做最小验证。
5. 回写真正有持续价值的文档。
6. 做阶段验收，并决定下一轮还是正式收口。

以下情况必须拆成下一轮：

- 需要新增第二个实现角色，但契约还没锁。
- 需要从兼容修正升级为对象建模或 schema 改造。
- 需要从阶段验收升级为正式收口。
- 需要从当前主题切换到新主题。

硬边界：一轮里最多只有一个主动作。页面重构、接口改造、数据模型重构、文档治理升级，不得同时并列为主动作。
