# Backend Guidelines

## 目标
保持后端接口边界清晰、返回结构稳定、权限逻辑明确、对前端影响可控，并默认服务于“园区综合能源管理系统 / 智慧园区 EMS”主线。

---

## 当前产品主线

后端线程默认按园区能源管理方向推进，当前阶段重点建设以下能力：

1. 多能源数据采集
2. 分层计量与统计
3. 分项分析
4. 告警规则
5. 实时数据接口
6. 历史数据接口
7. 驾驶舱聚合接口

接口设计、数据模型和服务边界，优先围绕以下核心业务对象组织：

- 园区
- 区域
- 楼栋
- 设备
- 表计
- 能源介质（电、水、气、冷、热）
- 分项能耗
- 告警
- 实时负荷

当前阶段不把煤矿专属对象作为后端主线能力重点，不新增以矿井、瓦斯抽采、通风、排水等为中心的主流程建模；若现有代码中仍保留相关能力，默认按历史底座兼容处理，而不是继续扩大接口和 schema 影响面。

---

## 后端改动优先级

1. 先修接口不可用
2. 再修权限异常
3. 再修返回结构不一致
4. 最后才做内部重构

---

## 接口排查顺序

当前端反馈“按钮点了没反应，但疑似后端问题”时，按以下顺序检查：

1. 路由是否存在
2. 接口方法是否匹配
3. 权限是否拦截
4. 请求参数是否正确解析
5. service 是否执行
6. 返回状态码是否合理
7. 返回结构是否与前端预期一致
8. 异常是否被吞掉或包装错误

---

## 修改原则

- 优先保持 API 兼容
- 优先最小修复
- 非必要不改动公共 schema
- 非必要不调整全局依赖注入和主流程
- 若必须改动接口契约，必须写入 handoff
- 新增接口优先服务园区 / 区域 / 楼栋 / 设备 / 表计的多能源统计与分析，不继续把煤矿专属概念作为默认主线
- 驾驶舱、园区总览、区域楼栋能耗、告警中心等页面需要的聚合查询，应优先通过稳定接口收口，而不是散落在多个临时端点中

---

## 每次修改后需要说明

- 修改接口
- 修改文件
- 影响范围
- 对前端的联调说明
- 验证结果
- 剩余风险

---

## 不建议的行为

- 后端线程直接去改前端页面
- 为修一个点而顺手大重构
- 无文档说明就改返回字段名
- 无兼容方案就调整接口结构
- 在没有明确计划文档的情况下，继续扩张煤矿专属实体、接口契约或强行业化返回结构
