# 文档体系规范

> 用统一的信息架构管理项目文档，减少重复、过期和“找不到该写到哪里”的问题。

---

## 1. 目标

本规范解决以下长期问题：

1. 同类信息分散在多个目录，维护成本高
2. 一次性方案、稳定规范、历史记录混在一起，难以检索
3. 新加入成员或智能体无法快速判断文档应该新增还是更新

文档体系的目标是：

- 稳定规则有固定入口
- 阶段计划有固定模板
- 历史沉淀有清晰归档
- 用户文档、架构文档、运维文档继续按主题维持现状

---

## 2. 顶层分类规则

### 2.1 现有主题目录

以下目录继续承载“面向读者主题”的内容：

- `docs/01-新手入门/`：首次接触项目的启动、安装、初始化
- `docs/02-功能使用/`：功能说明、操作手册、业务流程
- `docs/03-开发与部署/`：开发、测试、部署、运维、上线
- `docs/04-故障排查/`：故障现象、定位路径、应急处理
- `docs/05-架构与设计/`：架构说明、模型设计、约束分析
- `docs/06-历史记录/`：已完成事项、阶段总结、历史变更
- `docs/07-快速参考/`：高频命令、清单、速查卡片

### 2.2 新增规则层目录

- `docs/guides/`：稳定规范与协作约定
- `docs/plans/`：计划模板、进行中方案、待执行改动计划

---

## 3. guides 与 plans 的边界

### 3.1 放入 `docs/guides/` 的内容

满足以下任意条件时，优先写入 `docs/guides/`：

- 内容预期可复用 3 次以上
- 约束的是“怎么做”，而不是“这次做了什么”
- 面向多人协作、长期维护或智能体执行
- 需要在多个功能或阶段中保持一致

示例：

- 文档分类规范
- 计划编写规范
- 提交、评审、验收约束
- 协作边界和最小验证要求

### 3.2 放入 `docs/plans/` 的内容

满足以下任意条件时，优先写入 `docs/plans/`：

- 针对一次具体改动的行动计划
- 改动范围跨多个模块或目录
- 存在明确阶段、风险、回滚或验收条件
- 需要在实施前对范围和边界达成共识

示例：

- 权限系统重构计划
- 前端 API 层收敛计划
- 部署链路补齐计划
- 文档体系建设计划

### 3.3 不应写入 guides 或 plans 的内容

- 纯历史复盘或完成总结：放 `docs/06-历史记录/`
- 功能使用说明：放 `docs/02-功能使用/`
- 架构背景分析：放 `docs/05-架构与设计/`
- 临时排障记录：放 `docs/04-故障排查/`

---

## 4. 文档新增与更新决策

新增文档前，按下列顺序判断：

1. 先确认现有文档能否增补，避免重复建文
2. 若内容属于稳定规则，放到 `docs/guides/`
3. 若内容属于具体改动方案，放到 `docs/plans/`
4. 若事项已经完成且主要用于回顾，归档到 `docs/06-历史记录/`

建议采用以下判断句：

- “以后遇到同类事情都要按这个规则做” → `docs/guides/`
- “这一次要按这个步骤推进并验收” → `docs/plans/`
- “这件事已经完成，留下记录备查” → `docs/06-历史记录/`

## 5. 命名规范

### 5.1 guides 文档命名

推荐使用中文语义化命名，结尾尽量落在以下模式：

- `...规范.md`
- `...指南.md`
- `...约定.md`

示例：

- `文档体系规范.md`
- `变更计划规范.md`
- `协作约定.md`

### 5.2 plans 文档命名

计划文档统一使用前缀，便于排序和检索：

```text
PLAN-YYYYMMDD-主题.md
```

示例：

- `PLAN-20260327-文档体系建设.md`
- `PLAN-20260328-权限治理补齐.md`

模板文件统一使用：

- `TEMPLATE.md`

## 6. 推荐文档结构

### 6.1 guides 文档建议结构

1. 背景
2. 目标
3. 适用范围
4. 规则正文
5. 示例或反例
6. 维护方式
7. 相关文档

### 6.2 plans 文档建议结构

1. 背景与问题
2. 目标与非目标
3. 范围
4. 实施步骤
5. 风险与回滚
6. 验收标准
7. 进度记录

---

## 7. 维护职责

### 7.1 更新触发条件

出现以下情况时，应优先更新规范，而不是只改一次性说明：

- 新增了跨模块协作方式
- 新增了新的文档类别
- 计划模板无法覆盖当前项目的常见改动
- AGENTS 执行方式与文档约定出现偏差

### 7.2 一致性要求

修改 `docs/guides/` 或 `docs/plans/` 后，至少同步检查：

- `docs/README.md` 是否仍可导航到新内容
- `AGENTS.md` 是否仍与规范一致
- 相关 README 是否需要补一个入口链接

---

## 8. 最小质量要求

所有新规范文档至少满足：

- 标题清晰，可通过文件名直接理解用途
- 开头说明“适用场景”和“不适用场景”
- 边界明确，不与现有目录重复
- 至少包含一个决策标准或模板，避免空泛描述
