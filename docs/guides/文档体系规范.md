# 文档体系规范

> 用统一的信息架构管理项目文档，减少重复、过期和“找不到该写到哪里”的问题。

---

## 1. 目标

本规范解决以下长期问题：

1. 一次性说明、稳定规则、历史记录混在一起，难以检索
2. 目录已经变化，但 README 和 guide 仍可能引用旧入口
3. 基础性说明文档容易快速过期，维护成本高

文档体系目标：

- 稳定规则有固定入口
- 当前执行有固定主区
- 历史占位有最小入口
- 基础说明文档不再默认长期维护

---

## 2. 顶层分类规则

### 2.1 当前有效目录

以下目录承载当前仍在维护的内容：

- `docs/guides/`：稳定规范与协作约定
- `docs/plans/`：当前主题计划、状态、交接、daily 快照
- `docs/archive/`：极简归档入口；仅在确有必要保留追溯材料时再使用

### 2.2 已下线目录口径

以下目录不再作为当前正式文档层维护：

- `docs/01-新手入门/`
- `docs/02-功能使用/`
- `docs/03-开发与部署/`
- `docs/04-故障排查/`
- `docs/05-架构与设计/`
- `docs/06-历史记录/`
- `docs/07-快速参考/`
- `docs/superpowers/`

若历史材料仍提到这些目录，默认按“旧结构背景”理解，不应据此恢复旧入口。

---

## 3. guides、plans、archive 的边界

### 3.1 放入 `docs/guides/` 的内容

满足以下任意条件时，优先写入 `docs/guides/`：

- 内容预期可复用 3 次以上
- 约束的是“怎么做”，而不是“这次做了什么”
- 面向多人协作、长期维护或智能体执行
- 需要在多个功能或阶段中保持一致

示例：

- 文档分类规范
- 计划编写规范
- 协作边界与验收约束
- 命名、脚本和设备建模规则

### 3.2 放入 `docs/plans/` 的内容

满足以下任意条件时，优先写入 `docs/plans/`：

- 针对一次具体改动的行动计划
- 改动范围跨多个模块或目录
- 存在明确阶段、风险、回滚或验收条件
- 需要在实施前对范围和边界达成共识

### 3.3 放入 `docs/archive/` 的内容

以下内容仅在“不能直接删除，但又不应继续留在主区”时，才考虑放入 `docs/archive/`：

- 已完成且暂时仍需保留的计划、分析、审计
- 暂时不能直接删除的一次性修复记录或阶段总结
- 仍有少量追溯价值、但不应继续出现在主导航的旧文档

默认策略：

- 能删就删，不强制归档
- 只有在明确存在追溯需求时，才把材料放入 `docs/archive/`
- `docs/archive/` 不再默认承接大批历史正文

---

## 4. 文档新增与更新决策

新增文档前，按下列顺序判断：

1. 先确认现有文档能否增补，避免重复建文
2. 若内容属于稳定规则，放到 `docs/guides/`
3. 若内容属于当前专题执行依据，放到 `docs/plans/`
4. 若内容主要用于追溯，放到 `docs/archive/`

建议采用以下判断句：

- “以后遇到同类事情都按这个规则做” → `docs/guides/`
- “这一次要按这个步骤推进并验收” → `docs/plans/`
- “这件事已经完成，但短期仍需保留最小追溯入口” → `docs/archive/`
- “这件事已经完成，后续不再需要” → 直接删除

---

## 5. 主入口维护纪律

1. `docs/README.md` 只保留当前有效目录入口，不继续挂失效目录
2. `docs/plans/current-status.md` 和 `docs/plans/handoff.md` 主区任意时刻只服务一个当前主主题
3. 每天任务结束后，状态与交接快照进入 `docs/plans/daily/YYYY-MM/`
4. 已完成专题若无继续追溯需求，优先直接删除；若需要最小历史占位，再考虑放入 `docs/archive/`
5. 已归档文档默认不再作为主导航入口引用

---

## 6. 命名规范

### 6.1 guides 文档命名

推荐使用中文语义化命名，尽量落在以下模式：

- `...规范.md`
- `...指南.md`
- `...约定.md`

### 6.2 plans 文档命名

计划文档统一使用：

```text
PLAN-YYYYMMDD-主题.md
```

### 6.3 archive 文档命名

若确有必要保留归档文档，保持原名即可；当前不要求为归档长期维护额外命名体系。

---

## 7. 最小质量要求

所有新文档至少满足：

- 标题清晰，可通过文件名直接理解用途
- 开头说明“适用场景”和“不适用场景”
- 边界明确，不与现有入口重复
- 至少包含一个决策标准、入口说明或模板

---

## 8. 一致性检查

修改 `docs/` 结构或主入口后，至少同步检查：

- [docs/README.md](../README.md) 是否仍可导航
- [AGENTS.md](../../AGENTS.md) 是否仍与当前结构一致
- [docs/guides/README.md](./README.md) 是否仍与目录口径一致
- [docs/plans/README.md](../plans/README.md) 是否仍符合主区 / daily / archive 分层
