# AI 多角色协作 SOP

> 适用于本仓库内的 Codex、Cursor 与人工协作者。用于统一多角色协作的启动、执行、归档、收口和主题切换动作。
>
> 本 SOP 负责治理层动作；若要在高频开发中判断角色分流、切换、并行边界与单轮闭环，请配合阅读 [Codex 五角色 Vibe Coding 框架](./five-thread-vibe-coding-framework.md)。
>
> 兼容口径：本文正式使用“角色”作为主名；若历史材料出现“线程”，默认按角色理解。

---

## 1. 文档目的与适用范围

本 SOP 用于解决以下问题：

- 角色职责清楚，但执行流程不统一
- `current-status.md` 与 `handoff.md` 容易累积历史噪音
- 当前主主题容易漂移，导致不同角色读取到不同执行主线
- Daily 归档已有实践，但缺少正式规范
- 缺少主题收口、归档和切换下一个主题的标准动作

本 SOP 适用于：

- 规则角色（原：规范线程）
- 预判角色（原：探索线程）
- 前端角色
- 后端角色
- 验收角色
- 参与本仓库协作的人工成员与 AI 协作者

本 SOP 约束范围仅限仓库协作和文档治理，不直接替代具体技术实现规范。

## 2. 角色定义

### 2.1 规则角色（原：规范线程）

职责：

- 维护产品定位、术语边界和协作规则
- 维护长期稳定的规范文档
- 审核执行边界是否偏离当前主主题
- 规定计划、归档、交接和验收的文档格式

输出位置：

- `AGENTS.md`
- `docs/guides/*`

### 2.2 预判角色（原：探索线程）

职责：

- 阅读代码、定位问题、拆解任务
- 明确影响范围、根因、边界和最小修复路径
- 为实现角色提供正式执行依据

输出位置：

- `docs/plans/PLAN-*.md`
- `docs/plans/current-status.md`
- `docs/plans/handoff.md`
- 必要时的专题分析文档

### 2.3 前端角色

职责：

- 执行前端页面、组件、状态、交互与路由改动
- 严格按当前主主题和正式 PLAN 实施
- 完成最小前端验证并回写结果

输出位置：

- `docs/plans/current-status.md`
- `docs/plans/handoff.md`

### 2.4 后端角色

职责：

- 执行接口、schema、service、权限和返回结构改动
- 严格按当前主主题和正式 PLAN 实施
- 完成最小后端验证并回写结果

输出位置：

- `docs/plans/current-status.md`
- `docs/plans/handoff.md`

### 2.5 验收角色

职责：

- 对照正式 PLAN、当前状态和交接信息做验收核对
- 判断当前主题是否达到阶段完成或正式收口条件
- 判断主区内容是否应归档、是否应切换下一个主题
- 补齐最终验证结论、剩余风险和后续接手建议

输出位置：

- `docs/plans/current-status.md`
- `docs/plans/handoff.md`
- 必要时补充到当前 `PLAN-*.md`

说明：

- 即使未单独开设“验收角色”，每个主题结束时也必须执行验收动作。

## 3. 文档分层规则

### 3.1 `AGENTS.md`

定位：

- 仓库级协作总约束
- 角色职责、基础工作顺序、产品主线和输出要求

要求：

- 保持稳定
- 只写长期有效规则
- 不写按天滚动的状态细节

### 3.2 `docs/guides/*`

定位：

- 长期稳定的规范层
- 适合沉淀 SOP、计划规范、脚本治理、前后端约束

要求：

- 面向长期复用
- 不写一次性执行日志
- 新规则优先更新已有文档，避免并列冲突

### 3.3 `docs/plans/PLAN-*.md`

定位：

- 当前主题的正式执行依据

要求：

- 一个 PLAN 只服务一个明确主题
- 复杂任务进入实现前，必须有明确的 `PLAN-*.md` 或等价执行依据
- 保存主题级目标、范围、非目标、风险、验收标准和进度记录
- 不按天堆叠日志

### 3.4 `docs/plans/current-status.md`

定位：

- 当前主主题的状态面板

硬规则：

- 任意时刻，主区只允许服务一个当前主主题
- 只保留当前仍在推进的状态、风险、验证结论
- 不承担长期存史职责

### 3.5 `docs/plans/handoff.md`

定位：

- 当前主主题的行动性交接面板

硬规则：

- 任意时刻，主区只允许服务一个当前主主题
- 只保留当前仍有行动价值的交接
- `handoff.md` 负责行动，不负责长期存史

### 3.6 `docs/plans/daily/YYYY-MM/*.md`

定位：

- 每天结束后的状态快照与交接快照

要求：

- 用于按日期追溯
- 不替代正式 PLAN
- 承担 `current-status.md` 与 `handoff.md` 的历史沉淀职责

### 3.7 `docs/archive/plans/*`

定位：

- 已完成且不再作为当前执行依据的主题计划、审计和分析

要求：

- 仅保留追溯价值
- 不再作为当前入口引用

## 4. 标准工作流

### 4.1 立项

满足以下任一条件时，应先建立正式 PLAN：

- 任务跨两个及以上模块
- 涉及接口、数据结构、部署、权限或监控
- 需要多角色协作
- 需要分阶段推进
- 存在非低风险边界

立项动作：

1. 新建或确认当前主题对应的 `PLAN-*.md`
2. 明确目标、非目标、范围、风险、验收标准
3. 明确当前主主题名称，避免并列主题混写

### 4.2 角色启动

所有角色启动前，必须先阅读：

- `AGENTS.md`
- `docs/plans/current-status.md`
- `docs/plans/handoff.md`
- 当前主题对应 `PLAN-*.md`
- 本角色对应 guide

启动后先做两项判断：

1. 当前任务是否属于园区能源管理系统主线
2. 当前任务是否属于当前主主题

若不属于当前主主题，应先由规则角色或预判角色判断是否新开主题。

### 4.3 预判

预判角色必须先输出可执行结论，再进入实现：

- 问题背景
- 影响范围
- 根因或关键假设
- 建议最小修复路径
- 风险与非目标

若任务复杂，必须先把上述内容沉淀进 `PLAN-*.md` 或等价执行依据。

### 4.4 规则收敛

规则角色在实现前应确认：

- 术语与对象边界一致
- 当前主主题表达一致
- 当前计划、状态、交接三处口径一致
- 未把历史残留主题继续扩张为当前主线

### 4.5 前后端实现

前端角色和后端角色必须遵循：

- 先读正式 PLAN，再实施
- 只做当前主主题范围内的最小必要改动
- 关键范围变化必须先回写正式 PLAN 与 `handoff.md`
- 验证后再回写 `current-status.md`

### 4.6 验收

验收动作必须核对：

- 正式 PLAN 的目标是否完成
- 非目标是否被遵守
- 验证是否完成
- 风险是否已收缩到可接受范围
- 是否仍需要新的交接动作

若没有独立验收角色，由当前收尾角色执行同等动作。

### 4.7 每日归档

每天任务结束后，必须执行 Daily 归档：

- `docs/plans/daily/YYYY-MM/YYYY-MM-DD-status.md`
- `docs/plans/daily/YYYY-MM/YYYY-MM-DD-handoff.md`

归档内容为当天结束时的状态快照与交接快照。

归档后要求：

- `current-status.md` 主区只保留次日仍需继续推进的当前态
- `handoff.md` 主区只保留次日仍有行动价值的交接

### 4.8 主题收口

主题达到阶段完成或正式完成时，必须执行收口判断。

收口动作见第 7 章。

## 5. `current-status.md` 与 `handoff.md` 的维护纪律

### 5.1 主区单主题原则

硬规则：

- 任意时刻，`current-status.md` 和 `handoff.md` 主区只允许服务一个当前主主题

禁止事项：

- 同时混写多个无直接从属关系的主题
- 把旧主题历史块持续保留在主区
- 把“暂时可能有用”的历史记录继续堆在主区

### 5.2 `current-status.md` 的维护纪律

必须包含：

- 当前总目标
- 当前阶段
- 当前阻塞
- 当前待办
- 当前验证结论
- 当前剩余风险

必须避免：

- 按日期累加大量旧状态块
- 把一次性分析细节当成长驻正文
- 把已经完成且不再行动的内容留在主区

### 5.3 `handoff.md` 的维护纪律

必须包含：

- 当前可执行交接对象
- 已知信息
- 建议处理方式
- 必要限制条件
- 仍需确认的风险

必须避免：

- 写成长期历史仓库
- 保留已经失效的交接
- 用 `handoff.md` 替代正式 PLAN

### 5.4 更新顺序

推荐顺序：

1. 先更新 `PLAN-*.md`
2. 再更新 `current-status.md`
3. 再更新 `handoff.md`
4. 每日结束时归档 Daily 快照

## 6. Daily 归档规则

### 6.1 归档触发时机

以下任一情况出现时，应执行归档：

- 当天工作结束
- 当前阶段完成
- 主区内容已明显包含历史快照

### 6.2 归档命名规则

- 状态快照：`docs/plans/daily/YYYY-MM/YYYY-MM-DD-status.md`
- 交接快照：`docs/plans/daily/YYYY-MM/YYYY-MM-DD-handoff.md`

### 6.3 归档内容要求

状态快照应保留：

- 当天目标
- 当天进展
- 当天验证
- 当天风险

交接快照应保留：

- 当天仍需交接的动作
- 当天限制条件
- 当天未解决风险

### 6.4 归档后的主区整理

归档不是复制后继续保留主区全文。

归档后必须同步清理主区，只保留：

- 当前主题的最新状态
- 当前主题仍需继续推进的交接

长期追溯优先查看：

- `docs/plans/daily/`
- `docs/archive/plans/`

---

## 7. 主题收口规则

### 7.1 收口判断触发条件

以下任一条件满足时，应执行收口判断：

- 正式 PLAN 的验收标准已满足
- 当前阶段工作已完成，主题暂不继续推进
- 当前主题已不再适合作为主区执行依据

### 7.2 必做判断项

主题完成后，必须执行以下判断：

1. 是否仍作为执行依据
2. 是否继续留在 `docs/plans/`
3. 是否迁入 `docs/archive/plans/`
4. 是否清空当前主区并切换到下一个主题

### 7.3 收口动作

若主题仍会继续被引用：

- 保留 `PLAN-*.md`
- 在 `current-status.md` 中只保留下一阶段当前态
- 在 `handoff.md` 中只保留下一阶段仍有行动价值的交接

若主题已完成且不再作为执行依据：

- 将正式 PLAN、审计或专题分析迁入 `docs/archive/plans/`
- 清理 `current-status.md` 主区
- 清理 `handoff.md` 主区
- 切换到下一个明确主主题

### 7.4 切换下一个主主题

切换前必须确认：

- 上一个主题已完成收口判断
- 当前主区不再混留上一个主题的执行内容
- 下一个主题已有明确 PLAN 或等价执行依据

---

## 8. 输出格式要求

每次任务结束时，至少补充以下内容：

1. 本次目标
2. 发现的问题
3. 修改文件
4. 验证结果
5. 剩余风险
6. 需要交接给谁

若属于收口动作，还应额外说明：

- 是否继续保留为当前主主题
- 是否已归档到 Daily
- 是否迁入 `docs/archive/plans/`

---

## 9. 推荐执行节奏

推荐节奏如下：

1. 立项当天完成正式 PLAN
2. 每个角色启动前完成必读动作
3. 每次实施前先核对主主题与正式 PLAN
4. 每次阶段性完成后回写状态与交接
5. 每天结束前完成 Daily 归档
6. 每个主题完成后执行一次正式收口判断

---

## 10. 非目标与禁止事项

本 SOP 的非目标：

- 不替代具体前端或后端编码规范
- 不替代产品需求文档
- 不记录一次性按天日志细节

禁止事项：

- 没有正式 PLAN 就让复杂任务直接进入实现
- 在 `current-status.md` 或 `handoff.md` 主区并列维护多个当前主主题
- 把 `handoff.md` 当长期历史库使用
- 用 `daily/*.md` 替代正式 PLAN
- 主题完成后不做收口判断
- 未归档历史块就继续向主区叠加新内容
