# 变更计划规范

> 在动手实施前，用统一的计划文档明确范围、边界、风险和验收，降低返工成本。

---

## 1. 什么时候必须先写计划

满足任一条件时，建议先在 `docs/plans/` 写计划，再开始实施：

1. 改动跨两个及以上模块或目录
2. 涉及接口、数据库、部署链路、权限或监控等高影响区域
3. 需要分阶段推进，不能一次完成
4. 需要多人或智能体协作
5. 用户明确要求“先规划再实施”

以下情况可以不单独建计划：

- 单文件小修复
- 纯文案修正
- 明确范围的小型重构且风险极低

---

## 2. 计划文档的目标

计划文档不是需求文档，也不是完成总结。它的作用是：

- 让实施前的范围可讨论
- 让执行中的边界可追踪
- 让完成后的验收可核对

计划文档应优先回答：

1. 为什么做
2. 这次做什么，不做什么
3. 先做哪几步
4. 如何判断完成
5. 风险出现时如何收缩或回滚

---

## 3. 标准结构

所有计划文档建议包含以下章节：

## 背景

说明现状、触发原因和上下文。

## 目标

明确本次计划想达成的结果。

## 非目标

列出本次明确不处理的内容，防止范围蔓延。

## 范围

列出涉及的目录、模块、文档或系统边界。

## 实施步骤

按可执行顺序拆分，优先使用 3 到 7 个阶段。

## 风险与回滚

列出高风险点、降级方案、回滚边界。

## 验收标准

使用可核对语句，例如：

- 新目录已建立并写入 README
- 索引文档已补充导航入口
- 相关执行说明与 AGENTS 约定保持一致

## 进度记录

记录实际执行状态，建议使用：

- `未开始`
- `进行中`
- `已完成`
- `已取消`

---

## 4. 拆分原则

### 4.1 步骤拆分

优先按“可独立提交、可独立验收”的粒度拆分，不按想法堆砌。

推荐拆分方式：

- 信息架构调整
- 模板与规范落地
- 导航和索引补齐
- 验证与收尾

### 4.2 范围控制

计划中必须显式写出：

- 本次允许修改的目录
- 本次禁止触碰的目录或模块
- 是否允许顺手修复非目标问题

如果未明确写出，默认不做范围外扩展。

---

## 5. 验收写法

验收标准应避免模糊表述。

不推荐：

- “文档更清晰了”
- “结构更合理”

推荐：

- `docs/guides/` 至少包含目录 README 和 2 篇规范文档
- `docs/plans/` 至少包含目录 README 和 1 个模板文件
- 根目录存在 `AGENTS.md`，并说明协作边界与文档落点
- `docs/README.md` 已能导航到新增目录

---

## 6. 执行中的更新规则

计划开始实施后，若出现以下情况，应直接更新计划文档：

- 范围扩大或收缩
- 验收条件变化
- 风险判断变化
- 某阶段被取消或替换

不要把关键决策只留在聊天记录中。

---

## 7. 与历史文档的关系

计划执行完成后：

- 若计划仍会继续复用，保留在 `docs/plans/`
- 若计划已彻底完成且后续不再需要，优先直接删除；只有在短期仍需追溯时，才考虑放入 `docs/archive/`

是否归档取决于它未来是否还会被当作执行依据，而不是取决于它是否“已经做完”。
