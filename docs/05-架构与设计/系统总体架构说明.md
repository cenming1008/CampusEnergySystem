 # 系统总体架构说明
 
 > 本文从整体视角梳理 MineEnergySystem 的运行架构，对各个功能在架构中的位置做系统化说明，并通过文字 + Mermaid 示意图的方式帮助理解。
 
 ---
 
 ## 一、系统整体视图（上下文与运行时）
 
 本系统围绕「**现场设备 → 采集/网关 → MQTT → 后端服务 → 数据存储 → 前端展示**」这一条主链路设计，主要参与者和关系如下：
 
 - **用户侧**
   - 通过浏览器访问 Web 前端页面（设备台账、多能源管理、大屏、报表等）。
   - 前端通过 HTTP 调用后端 FastAPI 的各类业务接口，通过 WebSocket 接收实时数据。
 
 - **现场侧**
   - 实际的电表、水表、传感器、PLC 等外部设备。
   - 本项目自带的采集网关程序 `scripts/python/device_gateway.py`，负责通过 Modbus TCP/RTU、HTTP、串口等方式从设备侧读取数据，并统一转成 JSON 上报到 MQTT。
 
 - **通信/中间件**
   - MQTT Broker（如 Mosquitto）：统一承接来自网关或设备的 JSON 上报。
   - HTTP：浏览器前端与 FastAPI 之间的业务接口调用。
   - WebSocket：后端主动向前端推送实时数据的通道。
 
 - **MineEnergy 后端**
   - FastAPI 主应用：提供认证、设备、能耗、位置、分组、维护、分析等 API。
   - 后台任务：MQTT Worker（消息消费/即插即用）、定时任务调度器（预测训练与更新）。
   - WebSocket 管理器：维护所有 WebSocket 连接并广播实时消息。
 
 - **数据与缓存**
   - PostgreSQL/TimescaleDB：存储设备台账、位置/分组关系、能耗时序、报警、维护、预测等业务数据。
   - Redis：主要用于认证 Session/JWT 等缓存场景。

 ## 二、后端内部分层架构与模块划分
 
 后端整体采用「**API 层 → Service 层 → Core 层 → Model 层**」的分层结构，核心思想是：
 
 - API 层只关心「路由和参数」；
 - Service 层承载主要业务逻辑；
 - Core 层提供数据库会话、安全、设备类型注册表、WebSocket 管理等基础设施；
 - Model 层定义 ORM 表结构，统一与数据库交互。

 - **预测/分析**：由 `scheduler` 定时调用相关 Service，写入预测类表。

 ## 三、设备接入与端到端数据流
 
 核心思路是所有外部设备的数据最终都统一为 **MQTT 上报的 JSON**，后端只消费 MQTT，并在内部完成入库、报警、推送等一系列动作。
 
 ### 3.1 设备 → 网关 → MQTT → 后端 → 前端（总链路）
 
 - 设备通过 Modbus TCP/RTU、HTTP、串口等协议向网关暴露数据。
 - 网关程序 `device_gateway.py` 按配置轮询各设备，解析原始寄存器/报文为项目内部统一字段（如 `voltage`、`current`、`power`、`energy` 等）。
 - 网关把这些字段连同 `device_code` / `device_id` 等信息拼成 JSON，发布到 MQTT 对应主题。
 - 后端的 MQTT Worker 订阅这些主题，消费消息，完成：
   - 设备识别与即插即用；
   - 能耗数据入库；
   - 报警检测；
   - WebSocket 实时推送。
 - 前端一方面通过 WebSocket 收实时数据，一方面通过 HTTP 查询历史和统计。

 ### 3.2 网关内部采集逻辑（device_gateway.py）
 
 网关采集脚本的核心职责是「**统一采集、统一格式化、统一上报**」，逻辑大致如下：
 
 - 启动时优先从 `config/gateway_devices.json` 加载设备列表（按类别分组），失败时退回到代码内 `DEFAULT_DEVICE_CONFIG`。
 - 连接 MQTT Broker（默认 `localhost:1883`），启动循环。
 - 周期性遍历每一个设备配置：
   - 根据 `protocol` 选择对应的实现：
     - `modbus_tcp`：通过 `pymodbus` 连接设备 IP/端口，按寄存器地址与类型读取电压、电流、功率、电量等。
     - `http`：通过 `requests` 访问设备 HTTP API，根据 `field_mapping` 做字段映射。
     - 其他协议（如 `serial`）在扩展后可同样接入。
   - 将采集结果与设备身份信息（一致的 `device_id` / `device_code`）以及 `timestamp` 组合为一条 JSON。
   - 统一发布到 MQTT 主题（默认 `mine/telemetry`）。
 
 对应的流程图：
 
 ```mermaid
 flowchart TB
     start[脚本启动 main()] --> LCFG[load_device_config]
     LCFG -->|有 gateway_devices.json 并解析成功| USE_FILE[使用配置文件设备列表]
     LCFG -->|无文件或失败| USE_DEFAULT[使用 DEFAULT_DEVICE_CONFIG]
 
     USE_FILE --> CONN_MQTT[连接 MQTT Broker]
     USE_DEFAULT --> CONN_MQTT
 
     CONN_MQTT --> LOOP[采集循环]
 
     LOOP --> FOR_DEVICE{遍历每个设备配置}
     FOR_DEVICE --> READ[read_device(config)<br/>按 protocol 选择实现]
     READ -->|protocol=modbus_tcp| MODBUS[read_modbus_tcp]
     READ -->|protocol=http| HTTP[read_http]

     MODBUS --> SENSOR_DATA[得到 sensor_data dict]
     HTTP --> SENSOR_DATA
     UNSUPPORTED --> NEXT_DEVICE[下一个设备]
 
     SENSOR_DATA --> BUILD_JSON[拼接 device_id/device_code/timestamp<br/>+ 采集数值]

 ```

 ## 四、后端后台任务与实时推送架构
 
 后端中与运行时最相关的两部分是 **MQTT 后台监听** 和 **定时任务调度**，二者在应用启动时一并初始化。
 
 ### 4.1 MQTT 后台监听 + WebSocket 推送
 
 - 应用启动时，在 FastAPI 的 lifespan startup 中调用 `start_mqtt_background`：
   - 连接 MQTT Broker；
   - 订阅主题 `mine/telemetry` 与 `mine/device/+/telemetry`；
   - 启动后台线程，进入 `loop_start` 等待消息。
 - 每当有 MQTT 消息到达：
   - 触发 `on_message` 回调，进入 `process_data` 主处理逻辑：
     - 解析 JSON 与时间戳；
     - 根据 `device_id` 或 `device_code` 找到设备，必要时自动创建设备；
     - 归一化电压、电流、功率、流量等字段为系统内部字段。
   - 调用 `EnergyService.save_energy_data` 写入 `EnergyData` 表，必要时写入 `CarbonEmission`。
   - 调用 `AlarmService.check_and_create_alarm`，根据阈值写入 `Alarm` 表。
   - 从刚插入的数据中抽取实时字段（设备 ID、关键测点值、时间戳），构造 WebSocket 消息。
   - 通过 `_mqtt_to_ws_callback` 将消息调度到主事件循环，由 `ConnectionManager.broadcast` 向所有 WebSocket 客户端推送。
 
 综合流程示意：
 
 ```mermaid
 flowchart TB
     APP_START[FastAPI 应用启动] --> LIFESPAN[main.py lifespan startup]
     LIFESPAN --> START_MQTT[start_mqtt_background]
     LIFESPAN --> START_SCHED[start_scheduler]
 
     START_MQTT --> MQ_CONN[连接 MQTT Broker<br/>订阅 mine/telemetry 等]
     MQ_CONN --> LOOP_MSG[后台线程 loop_start 等待消息]
 
     LOOP_MSG -->|MQTT 消息到达| ON_MSG[on_message 回调]
     ON_MSG --> PROCESS[process_data]
 
     PROCESS --> PARSE_JSON[解析 JSON/异常处理]
     PARSE_JSON --> RESOLVE_DEV[解析 device_id/device_code<br/>必要时自动创建设备]
     RESOLVE_DEV --> NORM_METRIC[归一化指标/时间戳]
 
     NORM_METRIC --> SAVE_ENERGY[EnergyService.save_energy_data<br/>写 EnergyData 表]
     NORM_METRIC --> CHECK_ALARM[AlarmService.check_and_create_alarm<br/>写 Alarm 表(可选)]
 
     SAVE_ENERGY --> BUILD_WS[抽取实时字段<br/>{device_id, voltage, current, ...}]
     CHECK_ALARM --> BUILD_WS
 
     BUILD_WS --> WS_CALLBACK[_mqtt_to_ws_callback<br/>在主事件循环中调度]
     WS_CALLBACK --> WS_BROADCAST[ConnectionManager.broadcast]
     WS_BROADCAST --> WS_CLIENTS[所有 WebSocket 客户端]
 
     WS_CLIENTS --> UI_UPDATE[前端实时刷新设备状态/曲线]
 ```
 
 ### 4.2 定时任务：预测训练与预测更新
 
 - `start_scheduler` 在应用启动时创建 `BackgroundScheduler`。
 - 若配置项 `forecast_auto_update` 启用：
   - 注册每天凌晨自动训练 LSTM 模型的任务；
   - 注册每小时自动更新预测结果的任务。
 - 训练任务会从历史 `EnergyData` 中抽取数据，训练系统总负荷及各设备的预测模型，必要时训练风光/气象预测模型。
 - 预测更新任务会定期写入或更新预测结果表，供前端分析和图表展示调用。
 
 对应示意图：
 
 ```mermaid
 flowchart TB
     APP_START2[FastAPI 应用启动] --> START_SCHED2[start_scheduler]
     START_SCHED2 --> CREATE_SCHED[创建 BackgroundScheduler]
     CREATE_SCHED --> CHECK_CONF{forecast_auto_update 是否启用?}
 
     CHECK_CONF -->|是| ADD_TRAIN[添加 LSTM 训练任务<br/>每天凌晨]
     CHECK_CONF -->|是| ADD_FORECAST[添加预测更新任务<br/>每小时]
     CHECK_CONF -->|否| SKIP[不添加预测相关任务]
 
     ADD_TRAIN --> SCHED_RUN[Scheduler.start]
     ADD_FORECAST --> SCHED_RUN
     SKIP --> SCHED_RUN
 
     SCHED_RUN -->|到训练时间| RUN_TRAIN[auto_train_lstm_models]
     RUN_TRAIN --> TRAIN_SYS[训练系统总负荷模型]
     TRAIN_SYS --> TRAIN_DEV[训练各设备预测模型]
     TRAIN_DEV --> TRAIN_WEATHER[训练风光/气象预测模型]
 
     SCHED_RUN -->|到预测更新时间| RUN_FORECAST[auto_update_forecasts]
     RUN_FORECAST --> UPDATE_SYS[更新系统负荷预测曲线]
     RUN_FORECAST --> UPDATE_DEV[更新各设备预测曲线]
 ```

 ## 五、主要业务功能在架构中的落点一览
 
 本节以「功能 → 架构」的方式，对常用功能映射到上面介绍的各层模块，方便查阅。
 
 ### 5.1 用户认证与权限
 
 - **API 层**：`auth.py` 提供登录与 Token 获取接口。
 - **Core 层**：`security.py` 负责密码校验与 JWT 生成/解析。
 - **数据层**：用户表定义在 `tables.py` 中。
 - **调用链**：登录时通过 `POST /auth/login` 完成认证；业务接口通过依赖 `get_current_user` 从 JWT 中解析当前用户。
 
 ### 5.2 设备接入与设备台账
 
 - **网关侧**：
   - `device_gateway.py`：负责从设备采集数据、转成 JSON、发 MQTT。
   - `config/gateway_devices.json`：按类别维护需采集的设备清单和寄存器/字段映射。
 - **后端侧**：
   - **API 层**：`devices.py` 提供设备创建、查询、编辑等接口。
   - **Service 层**：`DeviceService` 封装设备相关业务逻辑（包括 `create_device_smart` 等）。
   - **Core 层**：`DeviceRegistry` 存储设备类型元数据，辅助即插即用自动补全字段。
   - **数据层**：`Device` 表保存设备主数据，并通过外键与 `Location`、`DeviceGroup` 等建立关系。
 - **特点**：通过 MQTT Worker 的自动创建设备机制，系统支持「即插即用」。
 
 ### 5.3 多能源管理与碳排放计算
 
 - **API 层**：`energy.py` 提供能耗查询、统计分析接口。
 - **Service 层**：`EnergyService` 负责保存能耗数据、计算碳排放、生成统计指标。
 - **数据层**：
   - `EnergyData`：记录设备级别的时间序列能耗/电量等。
   - `CarbonEmission`：记录对应能耗产生的碳排放量。
 - **数据来源**：主要由 MQTT Worker 消费设备上报数据后，通过 `EnergyService.save_energy_data` 写入。
 
 ### 5.4 位置层级管理
 
 - **API 层**：`locations.py` 提供位置创建、树形查询等接口。
 - **Service 层**：`LocationService` 负责计算 `level`、`full_path`，生成位置树，以及统计每个节点下的设备数。
 - **数据层**：`Location` 表记录各层级节点，`Device.location_id` 建立设备与位置的从属关系。
 
 ### 5.5 设备分组管理
 
 - **API 层**：`device_groups.py`。
 - **Service 层**：`DeviceGroupService`。
 - **数据层**：
   - `DeviceGroup`：分组主数据（生产线、工段、区域等）。
   - `DeviceGroupMembership`：设备与分组的多对多关系表。
 - **应用场景**：按分组汇总能耗、查看某产线/区域下所有设备及其实时/历史数据。
 
 ### 5.6 设备维护与保养
 
 - **API 层**：`maintenance.py` 提供维护计划创建、开始、完成、查询即将维护等接口。
 - **Service 层**：`MaintenanceService` 实现状态流转、维护时长计算等逻辑。
 - **数据层**：`DeviceMaintenance` 表记录维护计划与执行情况。
 
 ### 5.7 报警管理
 
 - **后台入口**：每条 MQTT 消息在 `mqtt_worker.process_data` 中都会调用 `AlarmService.check_and_create_alarm`。
 - **Service 层**：`AlarmService` 封装报警阈值加载、条件判断以及报警记录写入。
 - **配置**：`config/settings.json` 中配置全局或按设备的电流、电压等阈值。
 - **数据层**：`Alarm` 表，用于记录报警事件。
 - **前端表现**：可在报警列表、大屏告警区、设备详情中展示。
 
 ### 5.8 预测与分析
 
 - **后台任务**：`scheduler.py` 中的训练与更新任务在固定时间触发。
 - **Service 层**：预测相关 Service 负责训练模型、生成预测结果。
 - **数据层**：预测数据通常存放在 `Prediction` 或其他专用表中，关联到具体设备/系统。
 - **前端表现**：在分析/预测视图中展示未来一段时间的负荷、能耗、风光发电等曲线。
 
 ### 5.9 报表与大屏
 
 - **API 层**：报表/分析相关路由负责按时间、位置、分组维度聚合数据，并支持导出。
 - **Service 层**：组合 `EnergyService`、`LocationService`、`DeviceGroupService` 等聚合统计。
 - **数据层**：基于 `EnergyData`、`CarbonEmission`、`Device`、`Location` 等多表 JOIN 统计，必要时将导出文件写入文件系统。
 - **前端表现**：
   - 大屏实时区域通过 WebSocket 接收实时消息更新；
   - 报表与历史曲线通过 HTTP API 查询数据库数据。
