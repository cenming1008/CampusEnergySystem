# 煤矿综合能源管理系统 - 关键功能链路说明

> 用于快速熟悉项目、面试/汇报时讲清「数据从哪来到哪去、关键模块如何串联」。

---

## 一、整体架构（一句话）

**前端（Vue3）通过 HTTP/WebSocket 访问 FastAPI；设备数据经 MQTT 上报，后端写库、做报警检测并实时推给大屏；控制指令经 API → MQTT 下发给设备。**

---

## 二、五条关键功能链路

### 1. 设备遥测数据上报 → 存储 → 实时大屏（核心数据流）

**一句话**：设备/模拟器发 MQTT → 后端解析、入库、做报警检测 → 同一批数据通过 WebSocket 推给前端大屏。

| 步骤 | 位置 | 说明 |
|------|------|------|
| 1. 数据入口 | 设备 / `simulator_unified.py` | 向 MQTT 主题发布 JSON：`mine/telemetry` 或 `mine/device/{device_code}/telemetry`，含 `device_id`/`device_code`、`voltage`、`current`、`power`、`energy`/`consumption` 等 |
| 2. 订阅与回调 | `app/services/mqtt_worker.py` | `start_mqtt_background(on_message_callback)` 订阅上述主题，收到消息后调用 `process_data(payload, topic, broadcast_callback)` |
| 3. 解析与设备解析 | `mqtt_worker._resolve_device_id` | 用 `device_id` 或 `device_code`（含 topic 中的 code）解析出内部 `device_id`；若开启自动创建设备且设备不存在，会通过 `DeviceService.create_device_smart` 创建设备 |
| 4. 入库 | `DeviceService.report_device_data` → `EnergyService.save_energy_data` | 按设备类型（`device_registry`）做字段映射与校验，写入 `EnergyData` 表（时序数据，TimescaleDB hypertable `devicedata`） |
| 5. 报警检测 | `AlarmService.check_and_create_alarm` | 同一 session 内根据 `config/settings.json` 的阈值做电流过载、电压越限检测，超限则写 `Alarm` 表 |
| 6. 实时推送 | `_mqtt_to_ws_callback`（main.py）→ `manager.broadcast` | 将 `{ type: "telemetry_update", data: { device_id, voltage, current, power, energy, timestamp } }` 通过 WebSocket 广播给所有已连接前端 |
| 7. 前端展示 | 前端连接 `ws://host/ws` | 收到 `telemetry_update` 后更新大屏/图表 |

**关键代码入口**：
- 启动时注册回调：`main.py` 的 `_lifespan_startup()` 里 `start_mqtt_background(on_message_callback=_mqtt_to_ws_callback)`
- 单条消息处理：`mqtt_worker.process_data`（解析 → 入库 → 报警 → 构造 ws_data → 调用 broadcast_callback）

---

### 2. 远程设备控制（下发链路）

**一句话**：用户在界面上点击启/停 → 前端调 API → 后端发 MQTT 控制指令到设备。

| 步骤 | 位置 | 说明 |
|------|------|------|
| 1. 前端请求 | 前端 | `POST /devices/{device_id}/toggle?active=true|false`（或等价「启停」接口） |
| 2. API | `app/api/endpoints/devices.py` → `toggle_device_status` | 校验设备存在，调用 `DeviceService.toggle_device_status(session, device_id, active)` 更新 DB 状态 |
| 3. 下发指令 | `mqtt_publisher.publish_control_command(device_id, action)` | `action` 为 `"start"` 或 `"stop"`，发布到主题 `mine/control/{device_id}`，payload：`{"command": action, "device_id": device_id}`，QoS 1 |
| 4. 设备侧 | 真实设备 / 网关 | 订阅 `mine/control/{自身 id}`，解析 `command` 执行启停 |

**关键代码**：`devices.py` 中 `toggle_device_status` 内 `publish_control_command(device.id, action_code)`；`mqtt_publisher.py` 内 `topic = f"mine/control/{device_id}"`。

---

### 3. 报警检测与处理链路

**一句话**：报警在「遥测入库」时同步检测并落库；查询、确认、统计通过报警 API 完成。

| 环节 | 位置 | 说明 |
|------|------|------|
| 触发 | `mqtt_worker.process_data` 内 | 每条遥测入库后同一 session 内调用 `AlarmService.check_and_create_alarm(session, device_id, data, timestamp)` |
| 阈值 | `config/settings.json` | `default`：默认电流上限、电压上下限；`device_thresholds.{device_id}`：按设备覆盖 |
| 检测逻辑 | `alarm_service.check_and_create_alarm` | 电流 > `current_max` → 过载报警；电压 超出 `voltage_min`~`voltage_max` → 电压异常报警；每条写入 `Alarm` 表 |
| 查询/确认 | `app/api/endpoints/alarms.py` | `GET /alarms`（未解决列表等）、`POST /alarms/{id}/resolve` 等，由 `AlarmService` 的 `get_unresolved_alarms`、`resolve_alarm` 等实现 |

**讲点时可以强调**：报警与数据在「同一条消息处理路径」上，保证实时性；阈值可全局 + 按设备配置。

---

### 4. 认证与鉴权链路

**一句话**：登录用账号密码换 JWT；需要鉴权的接口通过依赖注入校验 Token 并得到当前用户。

| 步骤 | 位置 | 说明 |
|------|------|------|
| 登录 | `POST /auth/login`（form: username, password） | `app/api/endpoints/auth.py`：查 `User` 表、`verify_password`（Bcrypt），通过则 `create_access_token(data={"sub": username})` 返回 `access_token` |
| 携带 Token | 前端 | 请求头 `Authorization: Bearer <access_token>` |
| 鉴权依赖 | `app/api/deps.py` | `get_current_user(token, session)`：OAuth2PasswordBearer 取 token → jwt.decode → 用 `sub` 查 User；失败抛 `AuthenticationException` |
| 路由挂载 | `app/main.py` | 除 `/health`、`/auth` 外，业务路由统一 `dependencies=[Depends(get_current_user)]`，即「需登录才能访问」 |

**关键点**：Token 为 JWT，密钥与算法在 `app/core/settings.py`；密码存库为 Bcrypt 哈希（`app/core/security`）。

---

### 5. 数据分析与预测链路

**一句话**：分析基于已入库的 `EnergyData` 做统计与今日能耗；预测通过统一适配器选算法（含 LSTM）读历史数据并返回预测结果。

| 功能 | 入口 | 说明 |
|------|------|------|
| 设备分析 | `GET /analysis/{device_id}` | `AnalysisService.analyze_device`：查设备 + 最新一条 `EnergyData`，算当日能耗与费用（峰谷平电价），返回当前功率、电压、电流、今日能耗/费用等 |
| 负荷预测 | `POST /forecast/load?device_id=&hours=&algorithm=` | `ForecastAdapter.forecast_load`：从 `EnergyData` 取历史，支持 `moving_average`、`linear_regression`、`lstm` 等，返回未来若干小时预测值 |
| 风光预测 | `POST /forecast/renewable/{solar|wind}` | 同适配器，按类型做光伏/风电预测；LSTM 训练、数据生成等见 `docs/LSTM完整使用指南.md` |

**数据来源**：均为 TimescaleDB 中的 `EnergyData`（表名映射为 `devicedata` 的 hypertable）；预测还会写 `Prediction` 表做记录。

## 三、核心模块与文件速查

| 模块 | 主要文件 | 职责 |
|------|----------|------|
| MQTT 接入 | `app/services/mqtt_worker.py` | 订阅遥测主题、解析、入库、报警、触发 WebSocket 广播 |
| MQTT 下发 | `app/services/mqtt_publisher.py` | 向 `mine/control/{id}` 发布启停等控制指令 |
| 设备与数据 | `app/services/device_service.py`、`energy_service.py` | 设备 CRUD、统一数据上报接口、能源数据落库与查询 |
| 设备类型 | `app/core/device_registry.py` | 设备类型注册表（负荷、光伏、水表、热表等）及必需/可选字段 |
| 报警 | `app/services/alarm_service.py` | 阈值检测、报警创建、查询、确认 |
| 实时推送 | `app/core/socket_manager.py`、`main.py` 的 `/ws` 与 `_mqtt_to_ws_callback` | WebSocket 连接管理与 MQTT→WS 广播 |
| 认证 | `app/api/endpoints/auth.py`、`app/core/security.py`、`app/api/deps.py` | 登录、JWT 签发与校验、get_current_user |
| 分析/预测 | `app/services/analysis_service.py`、`app/services/forecast_adapter.py` | 设备分析、负荷/风光预测统一入口 |

## 四、讲解时可用的「金句」

1. **数据流**：「设备数据只进一次 MQTT，我们在这条链路上同时完成入库、报警和实时推送，所以大屏和报警都是实时的。」
2. **控制流**：「控制是反过来的，前端调我们 API，我们只负责把指令原样发到 MQTT，设备自己订阅自己的 control 主题执行。」
3. **扩展性**：「设备类型在 `device_registry` 里注册，新类型只要加配置和字段映射，遥测解析和入库是统一的。」
4. **安全**：「除了健康检查和登录接口，其它 API 都挂上 JWT 依赖，前端带 Token 访问；密码是 Bcrypt 存库。」
5. **分析/预测**：「分析和预测都基于同一套时序数据 EnergyData；预测通过 ForecastAdapter 可以切算法，包括 LSTM，训练和用法文档里有专门说明。」

---

## 五、建议的讲解顺序（约 5 分钟版）

1. **项目定位**：煤矿/工业场景的能源监控与管理，设备数据上云、实时看板、远程控制、报警、分析与预测。
2. **技术栈**：FastAPI + Vue3，TimescaleDB 存时序，Redis 缓存/会话，MQTT 接设备。
3. **数据上报链路**：MQTT → mqtt_worker（解析、入库、报警）→ WebSocket 推大屏；强调「一条消息、三个结果」。
4. **控制链路**：前端 → API → mqtt_publisher → `mine/control/{id}` → 设备。
5. **认证**：登录拿 JWT，业务接口统一依赖 get_current_user。
6. **扩展点**：设备类型注册表、报警阈值配置、预测算法适配器。
