# 第一节：串口（RS-232 / RS-485）

## 1.1 概念与定位

- **串口** = 在一条（或一对）线上**按位依次**传输数据，常见物理层有：
  - **RS-232**：点对点、全双工、±12V 电平、DB9，距离短（十几米）。
  - **RS-485**：差分 A/B 线、**半双工**、可挂多台设备（总线）、抗干扰好、距离可达百米以上。
- **谁和谁通信**：两台设备，A 的 TX 接 B 的 RX，B 的 TX 接 A 的 RX，GND 共地（至少 3 根线）。
- **层次**：串口只传**字节流**，不规定含义；上面再跑**协议**（如 Modbus RTU、自定义文本/二进制）。  
  详见：[串口通信入门](./串口通信入门.md)、[串口通信精通版](./串口通信精通版.md)。

## 1.2 必须一致的参数

| 参数     | 含义           | 常见取值        |
|----------|----------------|-----------------|
| 波特率   | 每秒传输的位数 | 9600、19200、115200 |
| 数据位   | 每字符位数     | 8               |
| 停止位   | 每字符后的停止位数 | 1           |
| 校验位   | 奇/偶/无       | 无（N）         |

**常见组合**：**9600 8N1**（9600 波特率，8 数据位，无校验，1 停止位）。设备手册里常写「9600, 8, N, 1」。

## 1.3 一帧长什么样（UART 字帧）

- 每传**一个字节**的格式：**起始位(1) + 数据位(8) + 校验位(0或1) + 停止位(1)**。  
  例如 8N1：一帧 = 1+8+0+1 = **10 位**。  
- 接收方用**相同**波特率在每位中间采样，才能正确还原字节。波特率误差一般要在 ±2% 以内，否则易错位、乱码。

## 1.4 帧边界与粘包/半包（应用层）

- 串口给你的是**连续字节流**，没有「第几帧」的标记。应用层要自己**定界**：
  - **按行**：设备每行以 `\r\n` 结尾 → 用 `readline()` 按行读。
  - **按长度**：协议规定「前 2 字节表示本帧长度」→ 先读 2 字节，再读「长度」个字节。
  - **按超时**：连续一段时间无数据认为一帧结束（如 Modbus RTU 的 3.5 字符时间）。
- **粘包**：多帧连在一起，一次 `read()` 拿到多帧，要按上面规则**拆帧**。  
- **半包**：一帧没收完就 `read()`，只拿到半帧，要**缓冲拼接**，凑满一帧再解析。

## 1.5 字节序（多字节数据）

- 若协议里「2 字节表示一个数」「4 字节 float」：
  - **大端（Big-Endian）**：高字节在前，如 0x1234 → 线上顺序 `12 34`。工业/Modbus 常用。
  - **小端（Little-Endian）**：低字节在前，0x1234 → `34 12`。
- 设备手册会写「高字节在前」或「Low byte first」；解析时必须一致，否则数值错误。

### 步骤 4：在网关中对接串口设备（详细说明）

假设你要让你的网关程序（`scripts/python/device_gateway.py`）支持通过串口接入设备并采集数据，操作流程可以分为如下几步。

**推荐**：设备列表统一放在 **config/gateway_devices.json** 中按类别管理，新增设备只需编辑该文件并重启网关，无需改代码。详见 [config/README_gateway_devices.md](../../config/README_gateway_devices.md)。

1. **在配置里添加串口设备的配置项**  
   - 打开 **config/gateway_devices.json**，在 `categories.serial.devices` 中新增一项；若仍用代码内配置，则打开 `device_gateway.py` 的 `DEFAULT_DEVICE_CONFIG` 添加。示例（JSON 格式）：
     ```json
     {
         "device_id": 101,
         "device_code": "SENSOR001",
         "name": "温度传感器",
         "protocol": "serial",
         "port": "/dev/ttyUSB0",
         "baud": 9600,
         "parity": "N",
         "stopbits": 1,
         "bytesize": 8
     }
     ```

2. **实现串口协议的采集流程**  
   如果你的 device_gateway 程序还没有实现串口（`protocol == "serial"`）的支持，你可以这样理解并逐步添加代码：

   - 用 `pyserial` 打开串口，例如：
     ```python
     import serial

     ser = serial.Serial(
         port=device_conf["port"],
         baudrate=device_conf.get("baud", 9600),
         bytesize=device_conf.get("bytesize", 8),
         parity=device_conf.get("parity", "N"),
         stopbits=device_conf.get("stopbits", 1),
         timeout=1   # 秒
     )
     ```
   - 按你的设备协议，定期从串口里**读一帧数据**。这一帧的长度、边界和具体拆分办法，要看你的设备手册。最常见的定界算法有：
     - 固定长度（如总是8字节，一次 read(8)）
     - 以换行符结尾（如 read_until(b'\n') 或 readline()）
     - 前导和尾部字节（如0xAA开头、0x55结尾，循环查找）
     - 超时断帧（如无数据超时则认为一帧结束）

   - **解析收到的数据帧**  
     - 如果数据是明文，可以直接用 `.decode()` 变成字符串再 strip；
     - 如果是二进制协议，要用 `struct.unpack()` 拆解每一段，注意设备的「字节序」（大端/小端）；
     - 如果有校验码（如校验和/CRC），要先验证校验是否正确。

   - **拼成 JSON 并通过 MQTT 上报**  
     - 把解析出来的数据组装成类似
       ```python
       {
         "device_code": "SENSOR001",
         "voltage": xxx,
         "current": xxx,
         "timestamp": 当前时间
       }
       ```
     - 用网关已有的 MQTT 客户端，publish 发送到指定 topic。

3. **注意事项**  
   - **协议的一致性**：实际解析和读写流程要严格参考你设备文档的协议部分，比如一帧多少字节，数据区怎么解释，大小端、校验算法是什么等。
   - **出错调试**：如果读到的内容不正确，优先检查波特率/数据位/校验/停止位等参数，一定要和设备一致。

> 整体流程就是：  
> ①按手册配置 DEVICE_CONFIG → ②用 pyserial 打开串口 → ③循环读数据帧并解析 → ④组 JSON → ⑤发 MQTT  
> 如果还不明白，可以参考 `scripts/python/test_serial_port.py` 里的最小读写代码，或参考本目录下的[串口通信精通版](./串口通信精通版.md)文档。

# 第二节：Modbus（RTU / TCP）

## 2.1 概念与定位

- **Modbus** 是**主从问答**的应用层协议：主机发一帧「请求」，从机回一帧「响应」。  
- **Modbus RTU**：跑在**串口**（RS-232/485）上，帧为二进制，帧尾 **CRC-16**；从站地址 1～247。  
- **Modbus TCP**：跑在 **TCP/IP** 上，把「从站地址」等放进 TCP 载荷，常用端口 **502**；通常不再单独做 CRC（依赖 TCP）。

## 2.2 寄存器

- **保持寄存器**（Holding Register）：可读可写，功能码 **03** 读、06 写单个、16 写多个；电表常把电压、电流、功率、电量放在固定地址。  
- **输入寄存器**（Input Register）：只读，功能码 **04** 读。  
- 每个寄存器 **16 位**；若设备用 **float32**，则占 **2 个连续寄存器**（4 字节），需按设备手册的字节序解码。

## 2.3 帧结构（RTU）

- **请求帧**（例：读保持寄存器 03）：  
  `[从站地址 1B][功能码 03 1B][起始地址 2B 大端][寄存器数量 2B 大端][CRC 2B 小端]`  
- **响应帧**：  
  `[从站地址][功能码][字节数][数据 N 字节][CRC]`  
- **帧间**：两帧之间至少 **3.5 个字符时间**（无数据），从站用这段静默判断上一帧结束。  
  字符时间 = 11 位 / 波特率（8N1 时一字符 10 位，按 11 位估算），如 9600 时约 1.14 ms/字符，3.5 字符约 4 ms。

## 2.4 帧结构（TCP）

- TCP 包 payload：**MBAP 头（7 字节）+ 与 RTU 相同的 PDU**（从站地址 + 功能码 + 数据），**无 CRC**。  
  MBAP 含：事务标识、协议标识 0、长度、单元标识（即从站地址）。  
- 端口：**502**。

# 第三节：MQTT

## 3.1 概念与定位

- **MQTT** 是**发布/订阅**消息协议，跑在 **TCP** 上；**Broker**（如 Mosquitto）负责转发。  
- **发布者**（设备/网关）向某个**主题（Topic）**发消息；**订阅者**（后端）订阅主题，从 Broker 收消息。  
- 特点：轻量、适合物联网、支持 QoS、发布与订阅解耦（发布者不知道谁在订阅）。

## 3.2 核心概念

- **Broker**：中间服务器，维护主题与订阅关系，转发消息。  
- **Topic**：层级字符串，如 `mine/telemetry`、`mine/device/1/telemetry`；订阅可用通配符 `+`（单层）、`#`（多层级）。  
- **QoS**：  
  - **0**：最多发一次，不确认；  
  - **1**：至少一次，有确认，可能重复；  
  - **2**：恰好一次，握手多，延迟大。  
  设备遥测常用 0 或 1。  
- **保留消息（Retained）**：Broker 保留该主题最后一条，新订阅者能立即收到。

## 3.3 在本项目中的角色

- **设备/网关**：向主题 **`mine/telemetry`** 或 **`mine/device/{device_code}/telemetry`** 发布 **JSON**（含 device_code、voltage、current、power、energy、timestamp 等）。  
- **后端**：订阅上述主题，收到后解析 JSON、入库、报警检测、再通过 WebSocket 推前端。  
- 格式约定见 [真实设备接入指南](./真实设备接入指南.md) 或后端 `mqtt_worker.process_data` 所需字段。

# 第四节：HTTP / REST

## 4.1 概念与定位

- **HTTP** 是请求/响应协议：客户端发**请求**（方法、URL、头、可选 body），服务端回**响应**（状态码、头、body）。  
- **REST** 常指用 HTTP 方法表达语义：GET 查、POST 创、PUT/PATCH 改、DELETE 删；数据常用 **JSON**。  
- 工控里：很多智能设备提供 **HTTP API**，返回 JSON（如电压、电流、流量、累计量），网关周期 GET 后做**字段映射**再发 MQTT。

## 4.2 常见状态码与方法

- **200**：成功；**201**：创建成功；**400**：请求错误；**401**：未认证；**404**：资源不存在；**500**：服务端错误。  
- **GET**：取数据，无 body；**POST**：提交数据，有 body（如 JSON）。

## 4.3 在本项目中的实践

### 步骤 1：用脚本或 curl 看设备返回

```bash
pip install requests

# 脚本
python scripts/python/test_http_device.py --url "http://192.168.1.101/api/data"

# 或 curl
curl -s "http://192.168.1.101/api/data"
```

- 记下返回的 **JSON 字段名**（如 `flowRate`、`totalVolume`、`voltage`），与系统需要的字段（如 `flow_rate`、`consumption`、`voltage`）对应。

### 步骤 2：在网关里配置 HTTP 设备

在 `device_gateway.py` 的 `DEVICE_CONFIG` 中，`protocol: "http"` 的配置示例：

```python
{
    "device_id": 12,
    "device_code": "WATER001",
    "name": "水表",
    "protocol": "http",
    "url": "http://192.168.1.101/api/data",
    "field_mapping": {
        "flow_rate": "flowRate",      # 设备字段名 → 系统字段名
        "consumption": "totalVolume"
    }
}
```

- `read_http()` 会用 `requests.get(config['url'])` 取 JSON，再按 `field_mapping` 把设备字段名映射成系统字段（flow_rate、consumption、voltage 等），然后与 Modbus 设备一样组 JSON 发 MQTT。

### 步骤 3：若需鉴权或 POST

- 设备若要求 **Header**（如 `Authorization: Bearer xxx`），在 `read_http()` 里加 `headers=...`。  
- 若需 **POST**，改为 `requests.post(url, json=...)`；具体看设备 API 文档。

# 阶段总结与面试准备

## 四协议对比（一句话）

| 协议   | 一句话 |
|--------|--------|
| 串口   | 物理层，按位传字节流；上面跑 Modbus RTU 或自定义协议，参数要一致。 |
| Modbus | 主从问答，寄存器模型，RTU 走串口+CRC，TCP 走网络 502。 |
| MQTT   | 发布/订阅，设备/网关发主题，后端订阅；解耦、适合物联网上报。 |
| HTTP   | 请求/响应，设备提供 API，网关 GET 后做字段映射再发 MQTT。 |

## 在本项目中的数据流（串联）

1. **设备侧**：真实设备通过 **串口（Modbus RTU）** 或 **Modbus TCP** 或 **HTTP** 把数据给网关（或设备直连 MQTT）。  
2. **网关**：`device_gateway.py` 按协议读设备 → 组成本系统约定的 JSON（device_code、voltage、current、power、energy 等）→ 发布到 **MQTT** 主题 `mine/telemetry`。  
3. **后端**：订阅 MQTT → 解析 JSON → 入库、报警检测 → WebSocket 推前端。  
4. **前端**：大屏/设备列表展示实时数据。

面试时可说：「我们现场有 Modbus 电表和 HTTP 水表，网关用 Modbus TCP/HTTP 读数据，统一转成 JSON 发 MQTT，后端只认 MQTT，这样设备侧协议可以多样，后端逻辑统一。」

## 常见面试题与参考答案

1. **你用过哪些通讯协议？**  
   串口（RS-485）、Modbus RTU/TCP、MQTT、HTTP；在能源监控项目里用 Modbus 读电表寄存器、HTTP 读水表 API，网关统一发 MQTT 给后端。

2. **Modbus 和 MQTT 的区别？**  
   Modbus 是主从、寄存器、适合设备现场总线、一问一答；MQTT 是发布订阅、适合设备/网关到平台、解耦；我们现场用 Modbus 采设备，网关转 MQTT 上报。

3. **串口通信要注意什么？**  
   波特率、数据位、停止位、校验两边一致；应用层要自己定界（行/长度/超时），注意粘包半包；多字节数据要搞清字节序。

4. **遇到过通讯问题吗？怎么排查？**  
   举例：波特率设错导致乱码，对照手册改 8N1 解决；Modbus 寄存器地址或 float32 字节序与手册不一致导致数值错，用 test_modbus_tcp 看原始寄存器再调解码；MQTT 收不到时用 mosquitto_sub 看主题是否有消息、后端是否订阅正确。
