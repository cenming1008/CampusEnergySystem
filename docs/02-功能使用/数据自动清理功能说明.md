# 数据自动清理功能说明

**文档创建时间**: 2026-01-24  
**适用版本**: 2.0.0+

---

## 📋 功能概述

系统支持**自动清理过期数据**，防止数据库无限增长。**手动清理**（前端按钮、API）说明见 [数据清理功能说明](./数据清理功能说明.md)。

### ✅ 已实现的自动清理

1. **日志文件清理** ✅
   - 应用日志：保留 7 天（可配置）
   - 错误日志：保留 30 天
   - 每天自动轮转和清理

2. **数据库数据清理** ✅ **新增**
   - 时序数据（EnergyData）：保留 90 天（可配置）
   - 报警记录（Alarm）：保留 180 天（可配置）
   - 统计数据（EnergyStatistics）：保留 365 天（可配置）
   - 碳排放记录（CarbonEmission）：保留 90 天（可配置）
   - 每天凌晨 3 点自动执行

## ⚙️ 配置说明

### 环境变量配置

在 `.env` 文件中添加以下配置：

```bash
# ==================== 数据清理配置 ====================
# 是否启用自动数据清理（默认：true）
ENABLE_AUTO_CLEANUP=true

# 时序数据保留天数（EnergyData、CarbonEmission等）
# 默认：90 天（3个月）
DATA_RETENTION_DAYS=90

# 报警记录保留天数（只清理已解决的报警）
# 默认：180 天（6个月）
ALARM_RETENTION_DAYS=180

# 统计数据保留天数（EnergyStatistics等）
# 默认：365 天（1年）
STATISTICS_RETENTION_DAYS=365

# 日志保留天数（应用日志）
# 默认：7 天
LOG_RETENTION_DAYS=7
```

### 配置说明

| 配置项 | 默认值 | 说明 | 建议值 |
|--------|--------|------|--------|
| `ENABLE_AUTO_CLEANUP` | `true` | 是否启用自动清理 | 生产环境建议 `true` |
| `DATA_RETENTION_DAYS` | `90` | 时序数据保留天数 | 根据存储空间调整（30-180天） |
| `ALARM_RETENTION_DAYS` | `180` | 报警记录保留天数 | 建议保留较长时间（90-365天） |
| `STATISTICS_RETENTION_DAYS` | `365` | 统计数据保留天数 | 建议保留1年以上 |
| `LOG_RETENTION_DAYS` | `7` | 日志保留天数 | 根据需求调整（3-30天） |

## 🔄 自动清理机制

### 清理时间表

| 清理类型 | 执行时间 | 清理内容 |
|---------|---------|---------|
| **日志清理** | 每天 00:00 | 删除超过保留期的日志文件 |
| **数据清理** | 每天 03:00 | 删除超过保留期的数据库记录 |

### 清理策略

#### 1. 时序数据清理（EnergyData、CarbonEmission）

- **清理条件**：`timestamp < (当前时间 - DATA_RETENTION_DAYS)`
- **优化**：如果使用 TimescaleDB，优先使用 `drop_chunks()` 函数（更高效）
- **影响**：删除后无法恢复，请根据需求设置合适的保留天数

#### 2. 报警记录清理（Alarm）

- **清理条件**：`timestamp < (当前时间 - ALARM_RETENTION_DAYS) AND is_resolved = true`
- **安全策略**：**只清理已解决的报警**，未解决的报警不会被删除
- **影响**：已解决的报警记录会被删除，但统计数据不受影响

#### 3. 统计数据清理（EnergyStatistics）

- **清理条件**：`stat_time < (当前时间 - STATISTICS_RETENTION_DAYS)`
- **影响**：历史统计数据会被删除，但不会影响实时统计

#### 4. 日志文件清理

- **清理条件**：文件修改时间超过 `LOG_RETENTION_DAYS`
- **机制**：使用 loguru 的 `retention` 参数自动清理
- **影响**：旧日志文件会被删除

## 🛠️ 手动清理

### 方法1：使用 Python 脚本

```python
from app.services.data_cleanup_service import cleanup_old_data

# 执行清理
result = cleanup_old_data()
print(result)
```

### 方法2：使用 SQL 命令

```bash
# 进入数据库
docker exec -it mine_energy_db psql -U admin -d mine_energy

# 清理 30 天前的时序数据
DELETE FROM energydata WHERE timestamp < NOW() - INTERVAL '30 days';

# 清理已解决的报警（超过 180 天）
DELETE FROM alarm 
WHERE timestamp < NOW() - INTERVAL '180 days' 
AND is_resolved = true;

# 清理统计数据（超过 365 天）
DELETE FROM energy_statistics 
WHERE stat_time < NOW() - INTERVAL '365 days';
```

### 方法3：使用清理脚本（日志）

```bash
# 清理 7 天前的日志
./scripts/shell/cleanup_logs.sh 7

# 清理 30 天前的日志
./scripts/shell/cleanup_logs.sh 30
```

## ⚠️ 注意事项

### 1. 数据备份

**重要**：自动清理会**永久删除**数据，无法恢复！

**建议**：
- 定期备份数据库（特别是清理前）
- 根据业务需求设置合适的保留天数
- 重要数据考虑导出到外部存储

### 2. 性能影响

- **清理时间**：大量数据清理可能需要较长时间
- **执行时间**：默认在凌晨 3 点执行，避免影响业务
- **数据库锁定**：清理过程中可能会短暂锁定表

### 3. TimescaleDB 优化

如果使用 TimescaleDB，系统会自动使用 `drop_chunks()` 函数：
- **优势**：比 DELETE 快得多
- **原理**：直接删除数据块，而不是逐行删除
- **要求**：表必须是 hypertable

### 4. 报警记录安全

- ✅ **未解决的报警不会被删除**
- ✅ **只清理已解决的报警**
- ✅ **保留时间较长**（默认 180 天）

## 🔧 故障排查

### 问题1：清理任务没有执行

**检查步骤**：
1. 检查配置：`ENABLE_AUTO_CLEANUP=true`
2. 查看调度器状态：
   ```python
   from app.services.scheduler_service import get_jobs
   jobs = get_jobs()
   print(jobs)
   ```
3. 查看日志：`grep "数据清理" logs/ems_app_*.log`

### 问题2：清理速度慢

**优化方案**：
1. 使用 TimescaleDB（自动使用 drop_chunks）
2. 在非高峰时段执行清理
3. 调整保留天数，减少清理量
4. 定期执行 VACUUM ANALYZE

### 问题3：数据被误删

**预防措施**：
1. 定期备份数据库
2. 设置合理的保留天数
3. 重要数据导出到外部存储
4. 监控清理日志
