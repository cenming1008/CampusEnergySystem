# 外部设备接入后系统详细工作流程

> 从「设备上电/接入」到「前端大屏看到实时数据」的完整数据流与各环节职责说明。

---

## 一、总览：两条入口路径

外部设备的数据进入本系统有两种常见方式：

| 方式 | 说明 |
|------|------|
| **经网关上报** | 这里的“网关程序”是指本项目中的 `scripts/python/device_gateway.py`，它负责通过 Modbus TCP/RTU、HTTP、串口等协议与外部设备通信，按照配置读取数据，将其封装为 JSON，并发布到 MQTT；后端只消费 MQTT 消息。 |
| **设备直连 MQTT** | 设备自身带 MQTT 客户端，按约定主题和 JSON 格式直接向 Broker 发布；无网关。 |

无论哪种方式，**后端统一只消费 MQTT**，后续流程一致。下面先按「经网关」这条最常用的路径展开，再说明「设备直连 MQTT」的差异，最后把「MQTT → 后端 → 前端」整段讲清。

---

## 二、路径 A：经网关接入（Modbus / HTTP / 串口）

### 2.1 网关启动与配置加载

1. 运行 `python scripts/python/device_gateway.py`。
2. **加载设备列表**：
   - 优先读取 **config/gateway_devices.json**，按类别（modbus_tcp、http、serial）展开为设备列表；
   - 如果配置文件不存在或解析失败，会尝试使用采集脚本（`device_gateway.py`）代码中的 **DEFAULT_DEVICE_CONFIG** 变量（见脚本中的 `load_device_config()` 实现）。实际生产环境应始终配置好 `gateway_devices.json`，默认配置仅供测试或紧急容错，配置文件未必支持所有功能。
3. 连接 **MQTT Broker**（默认 localhost:1883），连接成功后进入循环。

### 2.2 采集循环（每台设备）

对 **DEVICE_CONFIG** 中的每一项（每台设备）依次执行：

1. **按协议读设备**  
   - 根据 `protocol` 调用对应函数：  
     - `modbus_tcp` → `read_modbus_tcp(config)`：TCP 连设备，按 `registers` 读保持寄存器，解码为 voltage、current、power、energy 等；  
     - `http` → `read_http(config)`：GET 请求 `url`，按 `field_mapping` 映射成系统字段；  
     - `serial` → 若已实现，则打开串口、读一帧、解析。  
   - 得到一字典，如 `{"voltage": 220.5, "current": 10.2, "power": 2.25, "energy": 1000.0}`。

2. **组 MQTT 载荷**  
   - 将 `device_id`、`device_code`、`timestamp` 与上述字段合并为一条 JSON，例如：
     ```json
     {
       "device_id": 11,
       "device_code": "METER001",
       "timestamp": 1734567890.123,
       "voltage": 220.5,
       "current": 10.2,
       "power": 2.25,
       "energy": 1000.0
     }
     ```

3. **发布到 MQTT**  
   - 向主题 **mine/telemetry** 发布上述 JSON 字符串（或向 **mine/device/{device_code}/telemetry**，后端两种都订阅）。

4. **间隔**  
   - 所有设备轮询一遍后，休眠 **COLLECT_INTERVAL**（默认 5 秒），再开始下一轮。

至此，设备数据已进入 MQTT Broker，等待后端消费。

## 三、路径 B：设备直连 MQTT

- 设备（或设备侧的固件/网关）自带 MQTT 客户端，上电后连接同一台 **Broker**，按约定格式向 **mine/telemetry** 或 **mine/device/{device_code}/telemetry** 发布 JSON。
- 载荷中需至少包含 **device_code**（或 **device_id**），以及 **voltage / current / power / energy** 等字段（见 [真实设备接入指南](./真实设备接入指南.md) 或后端解析逻辑）。
- 无需本项目的 `device_gateway.py`；后端后续处理与「经网关」完全一致。

---

## 四、MQTT → 后端：订阅与处理

### 4.1 后端启动时

- 在 **app/main.py** 的 `_lifespan_startup()` 中调用 **start_mqtt_background(on_message_callback=_mqtt_to_ws_callback)**。
- **mqtt_worker** 连接 Broker，订阅：
  - **settings.mqtt_topic**（默认 `mine/telemetry`）；
  - **settings.mqtt_topic_wildcard**（默认 `mine/device/+/telemetry`）。
- 此后每条发到上述主题的消息都会触发 **on_message** → **process_data**。

### 4.2 单条 MQTT 消息的处理流程（process_data）

对每条收到的 MQTT payload（JSON 字符串）依次执行：

| 步骤 | 模块/函数 | 说明 |
|------|-----------|------|
| 1. 解析 | process_data | 将 payload 解析为 dict；若非法 JSON 或非对象则丢弃并打日志。 |
| 2. 解析设备身份 | _resolve_device_id | 若 payload 中有 **device_id** 且库中存在该设备，则直接用；否则用 **device_code**（或从 topic `mine/device/{code}/telemetry` 取 code）查库；若仍无且开启自动创建设备，则 ** _ensure_device_for_code**：按 device_type/数据推断类型，调用 **DeviceService.create_device_smart** 创建设备，得到 **device_id**。 |
| 3. 时间戳与指标归一化 | _parse_timestamp, _normalize_metrics | 解析 timestamp；提取/计算 voltage、current、power、energy 等，构造 **data_dict**（含 consumption、power、voltage、current、flow_rate、heat_flow 等所有本系统关心的字段，仅保留非 None）。 |
| 4. 写入时序库 | DeviceService.report_device_data | 在同一数据库 session 内，根据设备类型做字段映射与校验，调用 **EnergyService.save_energy_data**，将一条记录写入 **EnergyData** 表（时序库）。 |
| 5. 报警检测 | AlarmService.check_and_create_alarm | 同一 session 内，根据 **config/settings.json** 中的阈值（及可选的设备级阈值）检查电流、电压等，若超限则写 **Alarm** 表。 |
| 6. 组 WebSocket 推送内容 | process_data 内 | 从刚写入的 record 中取出 device_id、voltage、current、power、energy、timestamp，组成 **ws_data**。 |
| 7. 触发实时推送 | broadcast_callback(ws_msg) | 调用在 main 里注册的 **_mqtt_to_ws_callback**，将 `{ "type": "telemetry_update", "data": ws_data }` 交给 **ConnectionManager.broadcast**，向所有已连接的 WebSocket 客户端推送。 |

一条 MQTT 消息因此同时完成：**入库**、**报警判断**、**实时推前端**。

## 五、后端 → 前端：实时与历史

### 5.1 实时数据（WebSocket）

- 前端打开大屏/监控页时，会连接后端的 **WebSocket 端点 /ws**。
- **app/main.py** 中，`_mqtt_to_ws_callback` 在 MQTT 线程里被调用，通过 **asyncio.run_coroutine_threadsafe(manager.broadcast(msg_dict), _event_loop)** 把推送调度到异步循环。
- **ConnectionManager.broadcast** 向当前所有连接的 WebSocket 客户端 **send_json** 发送 `{ "type": "telemetry_update", "data": { device_id, voltage, current, power, energy, timestamp } }`。
- 前端收到后根据 **device_id** 更新对应设备在界面上的实时数值/曲线。

### 5.2 历史数据（HTTP API）

- 前端或报表需要历史曲线、统计时，通过 **HTTP API** 查询后端，例如：
  - 设备历史数据：**GET /devices/{device_id}/data**（时间范围、条数等）；
  - 设备统计：**GET /analysis/{device_id}** 等。
- 这些接口从 **TimescaleDB（EnergyData 等表）** 读已入库的数据，与 MQTT 实时写入的是同一份数据。

## 六、数据流简图

```
[ 外部设备 ]                    [ 本系统 ]
     │                               │
     │  Modbus TCP / HTTP / 串口      │
     ▼                               │
[ device_gateway.py ]                │
     │ 读寄存器/API/串口              │
     │ 组 JSON                       │
     │ publish                      │
     ▼                               │
[ MQTT Broker ]  ◄───────────────────┤ 或设备直连 MQTT
     │ 主题: mine/telemetry 等        │
     │ subscribe                    │
     ▼                               │
[ app/services/mqtt_worker.py ]      │
     │ process_data                  │
     │ ├─ 解析 device_id/device_code │
     │ ├─ 自动创建设备（若需要）       │
     │ ├─ DeviceService.report_device_data → EnergyData 表
     │ ├─ AlarmService.check_and_create_alarm → Alarm 表
     │ └─ broadcast_callback(telemetry_update)
     ▼                               │
[ app/core/socket_manager.py ]       │
     │ broadcast → 所有 WebSocket 连接
     ▼                               │
[ 前端 ] 实时大屏/设备列表            │
     │                               │
     │ 历史/统计：HTTP API            │
     ▼                               ▼
[ GET /devices/{id}/data 等 ]  →  [ TimescaleDB ]
```

## 七、关键配置与扩展点

| 环节 | 配置/位置 | 说明 |
|------|-----------|------|
| 网关设备列表 | config/gateway_devices.json | 按类别维护设备，新增设备加一项并重启网关。 |
| MQTT 主题 | 后端 settings.mqtt_topic、mqtt_topic_wildcard | 设备/网关需发布到相同主题。 |
| 即插即用 | settings.mqtt_auto_create_device | 为 True 时，未在库中的 device_code 会自动创建设备。 |
| 报警阈值 | config/settings.json | default 与 device_thresholds.{device_id}，电流/电压上下限。 |
| 设备类型推断 | mqtt_worker._infer_device_type | 自动创建设备时根据 payload 字段推断 load/water_meter 等。 |

---

## 八、小结（一句话版）

- **经网关**：设备 → 网关按 config 轮询读数据 → 组 JSON 发 MQTT → Broker → 后端 **mqtt_worker** 解析、解析/创建设备、入库、报警、WebSocket 广播 → 前端实时展示；历史数据走 HTTP API 查库。
- **设备直连 MQTT**：设备直接向同一 Broker、同一主题发约定 JSON，后端及之后流程与上相同。
- **一条消息**在后端被用三次：**写 EnergyData**、**可能写 Alarm**、**推 WebSocket**，保证实时与历史一致。
