# 真实设备接入指南

> 当前项目的数据来源可以是**模拟器**（`simulator_unified.py`）或**真实设备**。只要把真实设备的数据按约定格式发到 MQTT，后端就会像处理模拟器数据一样入库并推送到前端。本文说明如何接入真实设备。

---

## 一、数据流概览

```
真实设备（电表/水表/传感器等）
    ↓ 协议：Modbus TCP、HTTP、串口等
采集程序 / 网关（本机或工控机）
    ↓ 发布到 MQTT
MQTT Broker（mine/telemetry）
    ↓ 后端已订阅
后端 MQTT Worker → 解析 → 写入数据库 + 告警检测 → WebSocket 推前端
```

**要点**：后端和前端**不需要改**，只要有一条「采集程序」把真实设备的数据**按下面格式**发到 MQTT 即可。采集程序可以是你自己写的、也可以是本仓库自带的 `device_gateway.py` 或第三方网关（如 Node-RED、工业 IoT 网关）。

---

## 二、设备来源：手动添加 或 即插即用（自动创建）

### 方式 A：即插即用（推荐）

**无需事先在系统里添加设备**。只要设备或采集程序向 MQTT 上报带 **device_code**（设备唯一编码）的遥测数据，后端在**首次收到**时会**自动创建设备**并开始记录数据。

- 默认开启，可通过环境变量关闭：`MQTT_AUTO_CREATE_DEVICE=false`。
- 自动创建设备时：名称为 `device_name` / `name`（若 MQTT 携带）或 `设备-{device_code}`；设备类型可根据数据推断（电力/水表/热表等），或由 MQTT 字段 `device_type` 指定（如 `load`、`water_meter`）。
- 之后在前端「设备台账」中可看到该设备，并可修改名称、位置等。

### 方式 B：先登记再上报

每条上报的遥测数据也可以对应**系统中已存在的设备**（适合提前规划台账的场景）。

1. **在系统里创建设备**  
   - 方式一：在前端「设备台账」里手动添加。  
   - 方式二：调用后端 API `POST /devices` 创建设备。  
   - 方式三：用脚本 `init_complete_system.py` 或 `demo_*` 初始化一批设备。

2. **记下「设备 ID」和「设备序列号」**  
   - **设备 ID**：数据库主键，如 `11`、`12`。  
   - **设备序列号 (sn)**：即设备唯一编码，如 `METER001`、`WATER001`。  
   - 上报 MQTT 时，要么带 **device_id**，要么带 **device_code**（与 `sn` 一致），二选一即可；后端会用它们解析出是哪个设备。

3. **设备类型与能源类型**  
   - 创建设备时选择的「设备类型」「能源类型」会影响后端校验：不同类型有不同**必需字段**（见下文「字段说明」）。  
   - 电力类一般需要 `voltage`、`current`、`power`、`consumption`（或 `energy`）；水/气/热等需要 `consumption` 及可选 `flow_rate`、`pressure` 等。

---

## 三、MQTT 约定（后端如何解析）

### 1. 主题

后端默认订阅：

- **主题一**：`mine/telemetry`（与模拟器相同）
- **主题二**：`mine/device/+/telemetry`（`+` 为单层通配符，可带设备编码）

你的采集程序**只需向其中任一主题发布**即可，推荐使用 `mine/telemetry`。

### 2. 消息格式：JSON 字符串

每条消息是一个 **JSON 对象**，UTF-8 编码。字段说明如下。

#### 必带字段（身份）

| 字段 | 类型 | 说明 |
|------|------|------|
| **device_id** 或 **device_code** | 二选一 | `device_id`：数据库中的设备主键（整数）。`device_code`：设备序列号；若开启即插即用，首次上报时自动创建设备（与 `device.sn` 一致）。 |

#### 即插即用时可选（首次上报）

| 字段 | 类型 | 说明 |
|------|------|------|
| **device_name** 或 **name** | 字符串 | 设备显示名称，不传则用 `设备-{device_code}`。 |
| **device_type** | 字符串 | 设备类型，如 `load`、`water_meter`、`heat_meter`；不传则根据数据推断。 |

#### 建议带上的字段

| 字段 | 类型 | 说明 |
|------|------|------|
| **timestamp** | 数字 | Unix 时间戳（秒），不传则用服务端当前时间。 |
| **consumption** | 数字 | 累计消耗量（如电量 kWh、水量 m³），**电力设备也可用 energy**，后端会转成 consumption。 |

#### 按设备类型可带的字段（电力）

| 字段 | 类型 | 说明 |
|------|------|------|
| voltage | 数字 | 电压，默认 380 |
| current | 数字 | 电流 |
| power | 数字 | 功率（kW），若无则后端用 voltage×current 估算 |
| energy | 数字 | 累计电量，可替代 consumption |

#### 按设备类型可带的字段（水/气/热/冷等）

| 字段 | 类型 | 说明 |
|------|------|------|
| flow_rate | 数字 | 瞬时流量 |
| pressure | 数字 | 压力 |
| temperature | 数字 | 温度 |
| supply_temp / return_temp | 数字 | 供/回水温度 |
| heat_flow / heat_power | 数字 | 热功率/热流 |
| cooling_power | 数字 | 冷量 |

**示例（电力）**：

```json
{
  "device_id": 11,
  "device_code": "METER001",
  "timestamp": 1709123456.789,
  "voltage": 380,
  "current": 25.5,
  "power": 9.69,
  "energy": 1234.56
}
```

**示例（水表，用 device_code 标识）**：

```json
{
  "device_code": "WATER001",
  "timestamp": 1709123456.789,
  "consumption": 567.8,
  "flow_rate": 2.3,
  "pressure": 0.3
}
```

只要设备在系统中存在且 **sn = device_code**，后端就会把这条记录写入能源数据表并参与告警、统计、大屏展示。

## 四、接入方式一：使用本仓库自带的设备网关（推荐）

项目里已经有一个 **设备网关采集脚本**，从真实设备读数据并转发到 MQTT，可直接复用或改配置使用。

### 1. 脚本位置与依赖

- **路径**：`scripts/python/device_gateway.py`  
- **依赖**：`pip install pymodbus paho-mqtt`（若用 HTTP 设备，还需 `requests`）

### 2. 配置设备列表

在 `device_gateway.py` 里修改 **DEVICE_CONFIG**，把真实设备的 IP、端口、寄存器或 HTTP 地址填进去；**device_id / device_code** 必须与系统中已创建设备一致。

**Modbus TCP 示例**：

```python
{
    "device_id": 11,
    "device_code": "METER001",
    "name": "智能电表",
    "protocol": "modbus_tcp",
    "host": "192.168.1.100",
    "port": 502,
    "slave_id": 1,
    "registers": {
        "voltage": {"address": 0x0000, "type": "float32"},
        "current": {"address": 0x0002, "type": "float32"},
        "power": {"address": 0x0004, "type": "float32"},
        "energy": {"address": 0x0006, "type": "float32"},
    }
}
```

**HTTP 示例**：

```python
{
    "device_id": 12,
    "device_code": "WATER001",
    "name": "水表",
    "protocol": "http",
    "url": "http://192.168.1.101/api/data",
    "field_mapping": {
        "flow_rate": "flowRate",
        "consumption": "totalVolume"
    }
}
```

### 3. 运行方式

- **本机**（能访问 MQTT Broker 和真实设备网络）：  
  `python scripts/python/device_gateway.py`  
  环境变量可选：`MQTT_BROKER`、`MQTT_PORT`（默认 localhost:1883）。

- **在 Docker 后端容器内跑**（若设备与 Broker 都在内网）：  
  需把设备网段打通（如 host 网络或同一 Docker 网络），再在容器内执行上述命令。

采集脚本会按 **COLLECT_INTERVAL** 秒周期读取设备并发布到 **mine/telemetry**，后端收到后自动入库、告警、推前端，无需改后端/前端代码。

---

## 五、接入方式二：自写采集程序或第三方网关

只要满足以下条件即可：

1. **能访问 MQTT Broker**：与后端使用同一 Broker（地址/端口见后端配置，如 `MQTT_BROKER`、`MQTT_PORT`）。
2. **向 `mine/telemetry`（或 `mine/device/<device_code>/telemetry`）发布 JSON 消息**，格式符合第三节。
3. **设备已在系统中创建**，且上报的 **device_id** 或 **device_code** 与库中一致。

可以用任意语言（Python、Node.js、C、嵌入式等）或工具（Node-RED、工业网关的 MQTT 功能等）实现；本仓库的 `device_gateway.py` 仅作为「协议 + 格式」的参考实现。

---

## 六、接入方式三：设备直连 MQTT（设备本身支持 MQTT 时）

若设备或边缘网关**自带 MQTT 客户端**，可直接发布到 `mine/telemetry`，无需经过单独采集程序。要求同上：  
消息为 JSON，且至少带 **device_id** 或 **device_code**，以及 **consumption**（或电力设备的 **energy**）等必选字段。

---

## 七、网络与部署注意

- **Broker 可达性**：采集程序（或设备）所在网络必须能访问到后端使用的 MQTT Broker（如 1883 端口）。
- **设备可达性**：运行 `device_gateway.py` 的机器必须能访问到 Modbus 设备 IP 或 HTTP 设备 URL。
- **防火墙**：若 Broker 在服务器上，需放行 1883（或你配置的端口）。
- **认证**：若 Broker 开启了用户名密码，需在环境变量或代码中配置与后端一致的 `MQTT_USERNAME`、`MQTT_PASSWORD`（后端在 `app/core/settings.py` 中读取）。

---

## 八、如何验证已接入成功

1. **看后端日志**：上报成功会有类似 `设备数据上报成功: 设备ID=xx` 的日志；若 device_id/device_code 找不到设备，会打印 `missing device_id/device_code, skipped`。
2. **看前端**：在「多能源管理」「设备台账」等页面刷新，应能看到该设备的最新数据和曲线。
3. **看数据库**：查 `energy_data` 表，应有对应 device_id 的新记录。

---

## 九、小结

| 步骤 | 说明 |
|------|------|
| 1. 系统中创建设备 | 前端或 API 创建设备，记下 **id** 和 **sn（device_code）**。 |
| 2. 选一种接入方式 | 使用 `device_gateway.py`、自写采集程序、或设备直连 MQTT。 |
| 3. 按格式发 MQTT | 主题 `mine/telemetry`，JSON 带 device_id 或 device_code + consumption/energy 等。 |
| 4. 网络与认证 | 保证采集端能连上 Broker，必要时配置用户名密码。 |

接入后，真实设备数据与模拟器数据走同一套管道：**MQTT → 后端 → 数据库 + WebSocket → 前端**，无需区分配置。
